# 05 · 玩家 AI 代打：设计与规划

> 状态：**设计稿 v0.2（2026-10-29）· M1 已落地（模式 B）**。v0.2 按用户裁定 U7 改为「客户端 + 服务器」形态：Agent 网关与模型中转从玩家本机搬到游戏服务器，并写入 Q1 / Q2 / Q3 / Q8 的裁定（§13）。M1 的服务器侧实现说明见 06 §13.2。
> 本文是「让玩家用 AI 来玩」这一特色的唯一设计依据；落地后的规则条款同步进 `SPEC.md` §9。服务器、多端、数据记录见 `docs/06-多端与服务器架构.md`。
> 与现有实现的关系：设置页里的「提示词 Agent」是本文模式 B 的雏形；`src/ai/planner.js`、`src/ai/codec.js`、`src/app/scheduler.js` 的异步控制器都会被复用（客户端和服务器各跑一份，06 §3.4）。

## 0. 一句话

**玩家写下自己的博弈思路，选定 AI 该多听自己的，然后交给 AI 去打**。AI 来源有两种：

| | 模式 A ·「用我的 Agent 玩」 | 模式 B ·「接入我的大模型」 |
|---|---|---|
| AI 是谁 | 玩家自己的长程 Agent（WorkBuddy / CodeBuddy / 豆包等能多轮自主执行的 Agent），用它自己配置的大模型 | 玩家提供 API 地址 + 模型名 + 密钥，由游戏直接调用 |
| 谁驱动 | **Agent 驱动**：Agent 循环地向游戏服务器要局面、交决策 | **游戏驱动**：游戏在决策点问模型「你下一步打算怎么走？」 |
| 玩家要做的 | 在游戏里展开**卷轴**，复制一段提示词，粘进自己 Agent 的输入框 | 在设置页填好模型信息，点「测试连接」 |
| 对局在哪跑 | **服务器宿主**；浏览器只观战（06 §3.2） | 客户端（M1）；调用经服务器中转 |
| 费用 | 玩家 Agent 自己的模型，游戏不产生费用 | 玩家自己的 key，**谁用谁付**（06 §7） |
| 密钥 | 游戏完全不碰（在玩家的 Agent 里） | 只交给服务器保管，网页不保存（§7.2） |
| 适合 | 已经在用 Agent 产品、想看「我的 Agent」上场的人 | 有 API key、想要更快节奏和更可控成本的人 |

两种模式共用：**同一份局面**、**同一份决策契约**、**同一套「玩家思路 + 自主度」**、**同一套引擎执行与自保闸门**。区别只在「决策从哪条线路来」。

## 1. 术语

| 词 | 含义 |
|---|---|
| 玩家 AI | 替玩家（座位 0）做决策的 AI，模式 A 或 B |
| 对手 AI | 座位 1–3 的 AI（模拟大模型 / HY4 等真模型 / 启发式），与本文无关的部分沿用 SPEC §7 |
| 玩家思路 | 玩家写的博弈策略文本（≤ 2000 字），外加可选的「硬约束」开关（§5.4） |
| 自主度 | AI 对玩家思路的发散程度，三档：**自主 / 结合 / 严格**（§5） |
| 决策点 | 游戏需要玩家 AI 给出新计划的时刻（§3.2） |
| 计划 | 一次决策的产物：去哪个目标、为什么、是否遵循了玩家思路 |
| 游戏服务器 | 06 定义的服务器：Agent 网关、模型中转、对局宿主、对战数据记录 |
| 服务器宿主 | 在服务器上运行的对局（内核 + 调度器 + 规划 agent），客户端锁步观战（06 §3.2） |
| 卷轴 | 模式 A 的界面：展开后显示一段可复制的提示词，以及接入状态 |
| 对局口令 | 模式 A 每局一个的随机令牌，只授权「这一局的这一座位」 |

## 2. 总体架构

```
 客户端（Web / H5 / 桌面）
 ├─ 模式 B：本地宿主 —— 内核 + 调度器 + planner（relay transport）──HTTPS /llm/v1──┐
 └─ 模式 A：远程观战 —— SSE 订阅对局流，本地内核锁步重算、渲染 ◄──SSE──────────┐   │
                                                                             │   │
 游戏服务器                                                                    │   ▼
 ├─ host       服务器宿主：内核 + 调度器 + planner（agent transport）────推流──┘  llm-relay ──► 服务商（玩家的 key）
 ├─ agent-gw   /agent/v1：把「待决策局面」交给外部 Agent，收回计划
 └─ store      对局记录、座位统计、用量
        ▲
        │ HTTPS + 对局口令（curl / 脚本 / MCP）
 玩家电脑上的 Agent（用它自己的大模型）
```

设计原则：

1. **内核是唯一的规则来源**。规则、结算、寻路都由确定性内核完成，外部 AI 只提供「计划」，无法直接改状态，也拿不到更多信息。
2. **一份契约，两条线路**。两种模式都走 `planner.js`：决策点判定、预算、生效时序（SPEC §7.5，第 t 回合请求、t+L 回合生效）、降级链全部复用。模式 A 只是服务器上一个「把请求转给外部 Agent」的 transport，模式 B 是客户端上一个「经服务器中转」的 transport。好处：两种模式行为一致，测试一套就够。
3. **决策粒度是「意图」，走路交给引擎**（理由见 §3.1）。
4. **谁用谁付**。服务器只转发、只记账，从不为任何人的模型调用付费（06 §7）。
5. **对局数据进服务器**。服务器宿主的对局天然在库；客户端宿主的对局结束后上传，由服务器重放校验（06 §6）。

## 3. 决策：问什么、什么时候问

### 3.1 问「下一段去做什么」，不问「下一格往哪走」（Q1 裁定：逐格模式不做）

「你下一步打算怎么走？」在本游戏里落成**「你下一段打算去做什么」**：选一个目标（某颗宝石 / 宝箱 / 回出口）并说明理由，引擎用 BFS 走过去，途中由引擎处理让路、绕路、受阻。

| | 逐格问（每回合一次） | 按意图问（决策点才问）【采用】 |
|---|---|---|
| 一局调用次数 | ≈ 375（附录 B 回合 P50） | ≈ 40–70（实测：假上游跑 351 回合，两个 AI 各 41 / 47 次） |
| 模式 A 时长（Agent 每轮 10–40 s） | 1–4 小时 | 7–45 分钟 |
| 模式 B 费用 | ×6–9 | 基准 |
| 走位质量 | 大模型在 128×128 网格上逐格寻路很差，容易撞墙、绕圈 | 寻路由 BFS 保证最短；大模型只做它擅长的取舍 |
| 玩家思路能否体现 | 思路被淹没在几百次机械移动里 | 每次决策都是一次「取舍」，正好对应玩家思路 |

### 3.2 决策点

沿用 SPEC §7.2 / §7.3（与对手 AI 完全同构，公平）：

- **开局**第 1 回合；
- **计划完成**：到达目标；
- **间隔**：距上次决策 8 回合（终盘区 6 回合）；
- **事件**：① 目标被别人拿走 ② 宝物刷新 ③ 连续受阻 ④ 体力告警 ⑥ 对手进入视野；每局事件上限 10、冷却 3 回合；
- 【新增】**玩家喊话**（§8.2，M3）：作为一种事件，占事件额度。

**生效时序**：第 t 回合发出、第 t+L（L = 2）回合生效；到点还没回来，游戏**等待**。因此对局结果与 AI 想多久、网络多快无关，严格回放照常可用（已有测试「回复晚到与同步回复得到同一局」）。

### 3.3 局面（AI 看到什么）

即现有 `buildPayload(map, obs, cfg)` 的输出，来自同一个 `observe()`，与对手 AI 看到的完全同构（SPEC §6，J01–J04）。关键字段：

- `self`：位置、体力、分数、各色宝石、成套数、出口、`distToExit`、`lowStamina`、`inEndgame`
- `gems[]` / `chest`：坐标，以及**导航事实** `dist`（我到它）、`back`（它到我出口）、`rivalsNearer`（视野内比我近的对手）
- `rivals[]`：分数、体力、宝石；位置只在视野 R = 9 内给出，否则只给 `lastSeen`
- `terrain`：自身周围的地形片

为两种模式新增的字段（只附在玩家 AI 的请求里）：

| 字段 | 含义 |
|---|---|
| `decisionId` | 本次决策的编号（模式 A 用于幂等） |
| `why` | 触发原因：`start` / `complete` / `interval` / `targetLost` / `refresh` / `blocked` / `lowStamina` / `sighted` / `note` |
| `plan` | 当前正在执行的计划（目标、理由、已执行回合数） |
| `memo` | 上次决策时 AI 留给自己的笔记（≤ 500 字），**模式 A 必需**：长程 Agent 不必记住整局历史 |
| `notes` | 玩家喊话（M3） |
| `budget` | 本局剩余决策次数 |
| `brief`（模式 A 默认） | 精简视图：只给 8 个最值得考虑的候选（按 `v/(d+1)` 排序）和对手摘要；完整局面用 `?view=full` 获取。控制长程 Agent 的上下文增长 |

### 3.4 决策契约 v1（两种模式相同）

```json
{
  "targetType": "gem | chest | exit",
  "target": { "x": 63, "y": 0 },
  "reason": "不超过 30 字",
  "follow": "yes | partial | override",
  "deviation": "follow 不是 yes 时必填，不超过 60 字",
  "memo": "可选，不超过 500 字（模式 A）"
}
```

校验顺序（任何一步失败都返回明确的错误文本，供 AI 修正）：

1. 能解析出 JSON（容忍代码块围栏和前后杂字，现有 `parsePlan`）；
2. 目标合法：当前存在的宝石 / 宝箱坐标，或自己的出口（现有 `validatePlan`）；
3. 硬约束（§5.4）：目标不违反玩家勾选的硬约束；
4. 自主度（§5.2）：严格档下 `follow = override` 不合格；
5. 通过 → 记录、按 §3.2 生效。

**自保闸门**（现有）：执行中如果走过去就回不了出口，引擎自动改回出口，记为「引擎安全覆盖」（不算 AI 偏离）。三档默认都开；见 §5.3。

## 4. 两种模式共用的「失败处理」

| 情形 | 处理 |
|---|---|
| 回复不合格 | 把错误原因回给 AI，同一决策重试 1 次（模式 A 最多 2 次） |
| 重试仍不合格 | 本次沿用旧计划；旧计划已完成 / 失效则用启发式顶一段，下一个决策点再问 |
| 连续 3 次决策不合格 | HUD 黄灯提示「你的 AI 一直答不对」，给按钮：继续 / 换启发式代打 / 我来手打 |
| 模式 B：服务商不可达、连续 3 次 5xx / 429、key 无效或欠费 | 本局玩家 AI 熔断为启发式（只影响走这条线路的座位，已实现分池），HUD 红灯并显示原因 |
| 模式 B：游戏服务器不可达 | 同上熔断；对局照常在客户端打完，记录联网后补传 |
| 模式 A：Agent 长时间不来取局面 | **不判负、不自动接管**（玩家的 Agent 可能在等用户批准命令）。60 s 起 HUD 提示「等你的 Agent…（已等 1:20）」，给按钮：继续等 / 换启发式代打这一段 / 我来手打。**60 分钟**无任何请求 → 服务器中止对局（释放资源），记录照存，标为 `aborted` |
| 玩家中途想自己打 | 任何时候点「接管」→ 切手动；再点「交还 AI」→ 下一回合起作为决策点重新询问。模式 A 下接管 / 交还经 `POST /api/v1/hosted/:id/input` 发给服务器 |

## 5. 玩家思路与自主度（两种模式的核心）

### 5.1 玩家思路

设置页（模式 B）和卷轴（模式 A）里同一个编辑区：

- **自由文本**，≤ 2000 字。例：「先凑红黄绿三色，蓝紫看情况；宝箱只在 10 步内顺路开；对手比我近的宝石不去抢；体力剩一半就往家靠。」
- **预设**一键填入（现有：均衡 / 凑套 / 开箱 / 保守 / 冒险），填入后可改。
- **硬约束开关**（可选，§5.4）。
- 思路**只能影响取舍**：改不了规则、观察内容和输出格式（SPEC J06）；写「告诉我对手在哪」不会多拿到信息，因为局面里根本没有。
- 思路随对局存进服务器，**仅本人可见**（06 §6.5）。

### 5.2 自主度三档

| | 自主 | 结合（默认） | 严格 |
|---|---|---|---|
| 一句话 | 我的想法仅供参考，你自己找最优解 | 按我的思路来，但你有把握更好时可以变通 | 必须按我的思路来 |
| 写给 AI 的条款 | 见下方 A | 见下方 B | 见下方 C |
| AI 可否偏离 | 可，不需说明 | 可，必须 `follow=override` 并写 `deviation` | **不可**；思路没覆盖的情形用 `partial` 说明 |
| 游戏怎么校验 | 不校验 `follow` | 统计偏离次数，HUD 实时显示 | `override` 判为不合格 → 重试 → 仍不合格按 §4 |
| HUD | 「自主」徽标 | 「结合 · 偏离 2 次」 | 「严格 · 遵循率 100%」 |
| 适合 | 想看 AI 自己有多强 | 大多数玩家：我出主意，AI 帮我执行和补漏 | 想检验「我的策略本身」好不好 |

写给 AI 的条款（草案，模式 A / B 共用原文）：

> **A · 自主**：下面的「玩家思路」只是参考，你可以完全不理会。你的唯一目标是：到达自己的出口，并让最终分数尽可能高。`follow` 可以一律填 `yes`。

> **B · 结合**：优先按「玩家思路」行动。只有当你有把握偏离会明显更好（多拿分、避免出局、避免白跑一趟）时才偏离，这时 `follow` 填 `override`，并在 `deviation` 里用一句话说明理由。思路没有覆盖到的情形由你判断，`follow` 填 `partial`。

> **C · 严格**：必须按「玩家思路」行动，即使你认为有更好的选择。思路没有覆盖到的情形，选最保守、最接近思路本意的做法，`follow` 填 `partial` 并说明。禁止填 `override`。体力安全由游戏兜底：如果目标会让你回不了出口，游戏会自动改为回家，你不需要为了安全违背思路。

提示词拼装顺序固定，玩家只能改第 4 段：

1. 规则（固定）
2. 决策契约与输出格式（固定）
3. 自主度条款（三选一，固定原文）
4. **玩家思路**（玩家写，截断到 2000 字）
5. 局面（每次决策时生成）

### 5.3 自保闸门与「严格」的关系

- 闸门是**引擎**行为，不是 AI 行为：目标会让你回不了出口 → 改回出口。三档都默认开。
- 设置里单独一个开关「允许冒险（关闭自保闸门）」，默认关。打开后，即使是严格档，AI 按思路走到体力耗尽也照做——这是玩家自己的选择。
- 闸门触发记为「引擎安全覆盖」，HUD 和报告里与「AI 偏离」分开显示，避免把引擎的保护算到 AI 头上。

### 5.4 硬约束（可选，引擎强制）

文本思路靠 AI 自律，AI 嘴上说 `follow=yes` 实际没照做，游戏没法从语义上识破（诚实边界）。所以给最常见的几条策略做成**开关**，由引擎在校验第 3 步直接过滤目标，任何自主度下都生效：

| 开关 | 引擎怎么执行 |
|---|---|
| 不开宝箱 | `targetType = chest` 判不合格 |
| 只追这些颜色 □红 □黄 □绿 □蓝 □紫 | 其他颜色的宝石判不合格 |
| 回家余量 ≥ X%（默认 30%） | 目标须满足 `stamina ≥ dist + back × (1 + X%)` |
| 不抢对手更近的宝物 | `rivalsNearer` 非空的目标判不合格 |

硬约束同时写进提示词（让 AI 事先知道），减少无谓的重试。

### 5.5 温度

「发散程度」指 AI 离玩家思路多远，由自主度控制，**不等于**采样温度。

- 模式 B：温度默认 0（现有配置），「高级」里可调 0–1。
- 模式 A：游戏控制不了玩家 Agent 的温度，卷轴里注明。

## 6. 模式 A：卷轴 + 玩家自己的 Agent

### 6.1 玩家流程

1. 打开游戏（Web / H5 / 桌面任一端，需要联网）。
2. 设置页选「用我的 Agent 玩」→ 写思路、选自主度、（可选）勾硬约束、选对手。
3. 点「展开卷轴」：客户端调用 `POST /api/v1/hosted` 在服务器上建好这一局（先不开始），拿到 `matchId` 和**对局口令**；卷轴纸面上是为这一局生成的提示词。
4. 点「复制」→ 打开自己电脑上的 Agent（WorkBuddy / CodeBuddy …）→ 粘贴、发送。
5. Agent 先握手：卷轴底部的接入灯由「等待你的 Agent 接入…」变成「已接入：CodeBuddy」，**服务器开始对局**，客户端自动切到观战（Agent 没接上之前不开局，不会白白漏掉回合）。
6. 观战：HUD 显示 Agent 当前意图、理由、是否遵循思路；可以喊话（M3）、接管、交还。关掉页面不影响对局，重新打开「我的对局」即可接着看（06 §3.2）。
7. 结算：卡片上多一份「思路执行报告」（§8.3）；服务器告诉 Agent 对局结束，Agent 向玩家汇报名次与分数。对局记录自动在服务器存档。

在手机（H5）上也能走这个流程：在电脑上的 Agent 里粘贴提示词，在手机上观战。卷轴提供「发送到电脑」的二维码 / 链接，方便把提示词转到电脑上。

### 6.2 卷轴界面

- **造型**：沿用界面的三层框语言——上下两根深色漆木卷轴杆（两端哑金包头），中间米色纸面带纤维纹；展开动画约 600 ms（`prefers-reduced-motion` 下直接显示）；纸面右下角一枚封蜡印，印着座位色和本局口令后四位。
- **纸面内容**（从上到下）：
  1. 标题「致你的 Agent」+ 一句话说明；
  2. 三步上手：复制 → 粘贴到 Agent → 看下方接入灯；
  3. **思路编辑区 + 自主度三档选择 + 硬约束**（与设置页同一组件，改了实时刷新下方提示词）；
  4. **提示词正文**（等宽字体、可滚动），右上角大号黄铜按钮「复制」，旁边小按钮「复制精简版」（给上下文短的 Agent）；
  5. 接入灯：灰「等待接入」→ 绿「已接入：<Agent 名>」→ 黄「Agent 已 1:20 未响应」→ 红「口令已失效」；
  6. 兼容提示（折叠）：仅支持在你电脑上运行、能执行命令或发 HTTP 请求的 Agent；建议把卷轴里的命令设为「始终允许」，否则每次决策都要你点批准（一局 40–70 次）。
- **对局口令**：服务器生成（≥ 128 bit 随机），只授权这一局的座位 0；数据库只存哈希。口令在卷轴关闭前可点「换一个」作废重发；开局后只认已握手的那个 Agent（第二个握手返回 409）；对局结束 10 分钟后失效。

### 6.3 Agent 网关协议 v1（服务器上）

地址 `https://maze.aiquiz.games/agent/v1`（06 §12.1；本地开发时为 `http://127.0.0.1:5173/agent/v1`）；所有请求带 `Authorization: Bearer <对局口令>`；线上只接受 HTTPS；请求体 ≤ 64 KB；`/wait` 之外的接口每秒 ≤ 5 次；单个口令同时只允许一个 `/wait` 挂起。

| 方法 · 路径 | 作用 | 返回 |
|---|---|---|
| `GET /agent/v1/hello?agent=<名字>` | 握手；客户端接入灯变绿、服务器开始对局 | `{ok, matchId, seat, rulesVersion, contract, autonomy, decisionCap}` |
| `GET /agent/v1/wait?timeout=25` | 长轮询，等下一个决策点 | `{status:"decide", decisionId, turn, why, state, plan, memo, budget}` / `{status:"pending"}`（立刻再调）/ `{status:"ended", result}` / `{status:"aborted", reason}` |
| `POST /agent/v1/decide` | 提交决策（§3.4 契约 + `decisionId`） | `{ok:true, appliedTurn}` / `{ok:false, error, retriesLeft}` |
| `GET /agent/v1/state?view=full` | 随时看当前完整局面（只读，限频） | 同 `state` |
| `GET /agent/v1/manual` | 完整规则与契约说明（让提示词可以短一些） | Markdown 文本 |
| `GET /agent/v1/helper.mjs` | 助手脚本（见下） | JS 源码 |

- **幂等**：同一个 `decisionId` 重复提交，以第一次合格的为准，后续返回同一结果。
- **服务器侧**：服务器宿主里座位 0 的 planner 用 `agent transport`：决策点到了，就把请求挂到网关；收到合格回复即 `reply.deliver(...)`；不合格时走 planner 已有的 repair 流程（转成 `{ok:false, error}` 回给 Agent）。没有超时，只有 §4 的提醒和 60 分钟中止。
- **客户端侧**：只订阅对局流观战（06 §3.2），不参与决策。
- **怎么发请求**：Agent 用它手边的任何方式都行（curl、Python、Node、自带的 HTTP 工具）。为绕开 Windows PowerShell 下 curl 与 JSON 引号的麻烦，提供两种辅助：
  - 把决策写进文件再发：`curl.exe -s -X POST -H "Authorization: Bearer …" -H "Content-Type: application/json" --data-binary @decision.json <地址>/decide`；
  - 助手脚本（需要本机有 Node ≥ 18）：`curl.exe -s -o maze-agent.mjs <地址>/helper.mjs`，然后 `node maze-agent.mjs wait` / `node maze-agent.mjs decide --file decision.json`。地址和口令由卷轴写进命令参数，或从环境变量读取。
- **MCP 适配**（M3）：提供一个可在玩家本机运行的 MCP 服务（`maze_wait` / `maze_decide` / `maze_state` 三个工具，内部调用同一网关）；卷轴多一个「MCP 配置」页签，给出可复制的配置片段。

### 6.7 公平与诚实边界

- 网关只给 `observe()` 同源的局面，与对手 AI 看到的完全同构；地图种子、对手计划、视野外坐标不经网关暴露。对局在服务器上跑，Agent 无法改状态，也无法读到服务器内存。
- 但单人观战流是完整状态（客户端要靠它锁步渲染，06 §3.2）。同一位玩家理论上可以把观战画面里的信息转给自己的 Agent。单人非排位对局里这不影响别人，接受；排位与 PvP 改为按座位过滤的观察流（06 §10）。
- 记录里标注通道 `agent-external:<名字>`；Agent 自报的名字只作展示，不作身份证明。

## 7. 模式 B：接入玩家自己的大模型

### 7.1 玩家流程

1. 设置页选「接入我的大模型」。
2. 选服务商预设（自动填地址），填模型名、API key → 点「测试连接」：显示延迟、返回的模型名，以及一次示范决策（用开局局面跑一次，验证能按契约输出）。
3. 写思路、选自主度、（可选）硬约束 → 开始对局。
4. 对局在客户端跑；每个决策点，客户端经服务器中转（`POST /llm/v1/chat`）问模型；HUD 显示意图、理由、遵循情况；结算有报告，记录自动上传。

### 7.2 密钥怎么处理（项目铁律：密钥不进前端）

- 网页里的 key 输入框只在提交时用一次：`POST /api/v1/keys`（HTTPS）交给服务器，然后立刻清空输入框；网页不保存、不回显：不进 localStorage / IndexedDB / 对局记录 / 页面 DOM / 控制台。
- 默认「仅本次会话」：服务器只放在内存里，24 小时或退出登录后丢弃。
- 勾选「记住」：服务器用 AES-256-GCM 加密后入库，主密钥不进库、不进仓库（06 §7.2）。
- 任何接口只返回服务商、模型名和尾号（如 `sk-…3f9a`）；服务器日志打码；玩家随时可删。
- 桌面端（Electron，06 §8.2）可选「本机直连」：key 用系统钥匙串加密存在本机，由壳的主进程调用服务商，不经服务器，网页部分也拿不到 key。

### 7.3 服务商

统一走 **OpenAI 兼容的 `/chat/completions`**（现有代理已经是这个格式）。预设只帮玩家填地址，地址与模型名以各厂商文档为准，上线前逐个核对：

| 预设 | 地址（待核对） |
|---|---|
| 腾讯混元（HY4） | 凭证到位后填写（O9） |
| DeepSeek | `https://api.deepseek.com/v1` |
| 火山方舟（豆包） | `https://ark.cn-beijing.volces.com/api/v3` |
| 阿里云百炼（通义） | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| Moonshot（Kimi） | `https://api.moonshot.cn/v1` |
| OpenAI | `https://api.openai.com/v1`（服务器在中国大陆时可能连不通） |
| 本机 Ollama | 仅桌面端（Electron）的本机直连（服务器访问不到你电脑上的端口） |
| 自定义 | 玩家自填，只允许 `https://`，服务器做 SSRF 校验（06 §7.3） |

### 7.4 调用与费用（谁用谁付）

- 复用 `planner.js`：预算池与对手分开（已实现分池），玩家 AI 熔断不影响对手。
- 每局约 40–70 次调用；每次输入约 1–2k token、输出约 50 token（**待真模型实测**），一局约 6–15 万 token。设置页显示「预计每局调用次数 / token」，结算卡显示实际用量（从服务商回复的 `usage` 字段读取，06 §7.4）。
- 玩家可设「每局调用上限」，由预算池执行。
- **推理型模型**（先长时间思考再回答）：现有超时 8 s 不够。增加开关「这是推理模型」→ 超时放宽到 60 s、`max_tokens` 放宽。因为游戏在生效回合会等待，放宽超时只会让节奏变慢，不影响结果。（M1 落地值：经服务器中转的普通模型客户端超时 40 s、推理模型 85 s，依据见 06 §13.2。）

### 7.5 对手 AI 用谁的模型（Q3 裁定：谁用谁付）

服务器不替任何人付模型费用。对手（座位 1–3）可以：

- 用模拟大模型 / 启发式（默认，免费）；
- 用真模型（包括 HY4）：费用算在**开局玩家**自己的 key 上，界面明示「费用约 ×4」（06 Q11 已裁定）。
