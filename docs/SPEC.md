## 1. 场地与地图生成

### 1.1 坐标与距离 【实现】

- 坐标 `(x, y)`，x 向右、y 向下，范围 `0..127`；格索引 `y*128 + x`。
- 方向：`N(0,−1)` `E(+1,0)` `S(0,+1)` `W(−1,0)`；意图取值 `N|E|S|W|STAY`。
- **距离默认 = BFS 步数**（4 邻、墙不可通、不计角色占位）。只有「视野」用切比雪夫距离，「撒点最小间距」用曼哈顿距离。

### 1.2 座位、出生点、出口 【沿用】

| 座位 | 出生点 | 自己的出口 | 分配 |
|---|---|---|---|
| 0 | (2, 2) | (63, 0) | 左上 → 上边中点 |
| 1 | (125, 2) | (127, 63) | 右上 → 右边中点 |
| 2 | (125, 125) | (63, 127) | 右下 → 下边中点 |
| 3 | (2, 125) | (0, 63) | 左下 → 左边中点 |

- 就近 + 顺时针分配（左上到上、左两个边中点等距，按顺时针取上）。
- 玩家默认坐座位 0（`match.playerSeat`）【实现】。
- 出口常开；**别人的出口 = 普通地面**（可通行、可停留，无任何效果）。

### 1.3 生成流程（顺序固定）【实现】

1. **Growing Tree**：单元位于奇坐标 `(2i+1, 2j+1)`，`i, j ∈ 0..62`（最大到 125）；取点规则 newest 0.55 / random 0.35 / oldest 0.10。
   - 修正旧 `tools/sim/lib.mjs` 的 bug：它用 64×64 单元，坐标能到 127，把右边、下边的外圈挖成了走廊。
2. **Braid**：每个死胡同以 0.35 概率打通一面墙。
3. **房间**：4 个，边长 6–14，完全落在 `[2, 125]` 内。
4. **削墙**：内部墙格（`1..126`）以概率 `1 − thinKeep` 变地板。`thinKeep` 是标定值：**0.727**（`tools/calibrate.mjs`，400 种子，封边后密度均值 ≈0.355）。换生成器或改前三步参数必须重标。
5. **封边**：`x=0`、`x=127`、`y=0`、`y=127` 全部置墙。
6. **开洞**：
   - 出生点 3×3（半径 1）置地板；
   - 出口格 + 其内侧 1 格置地板，**开口宽度恰好 1**（不挖 3×3，避免外墙出现 3 格宽的口子）。
7. **回填孤岛**：不与出生点所在连通域相连的地板全部回填为墙。
8. **校验**（§1.4）。失败则 `attempt + 1` 重新生成，最多 20 次；全部失败则抛错并带上 seed。**重试不放松任何参数。** 第 attempt 次的迷宫流 = `subSeed(subSeed(seed, 1), attempt)`，撒点流 = `subSeed(subSeed(seed, 2), attempt)`（见 §12）。

### 1.4 开局校验（全部通过才可开局）

| ID | 条件 | 状态 |
|---|---|---|
| V1 | 全图地板单连通（步骤 7 后必然成立，仍需断言） | 【定】U4b |
| V2 | 每个出生格为地板，且 4 邻中 **≥2 个地板** → 开局不会四面受阻 | 【定】U4b；阈值 2 为【实现】 |
| V3 | 出口格为地板；出口两侧的外圈格为墙（开口宽 1）；内侧格为地板，且除出口外至少还有 1 个地板邻居 | 【定】U4b |
| V4 | 每个座位：出生点 → 自己出口的 BFS 距离 ∈ **[68, 108]** | 【沿用】 |
| V5 | 四条距离的 (最大 − 最小) / 均值 ≤ **0.35** | 【沿用】 |
| V6 | 封边后墙密度 ∈ **[0.347, 0.363]**（目标 0.355 ± 0.008） | 【沿用】 |
| V7 | 初始宝物撒点成功（§3.4） | 【实现】 |

- **门禁**：单次失败率 p 要满足 p²⁰ ≤ 10⁻⁶（约 p ≤ 0.50）。**阶段 1 实测 p ≈ 0.05**（1000 种子里 5.0% 需要重掷，平均尝试 1.06 次；拒因 V4 35 / V4+V5 7 / V5 12 / V6 3），远低于门槛。
- **可选约束 `maze.forbidDeadEnds`**：消除全部死胡同。**阶段 1 结论：不需要，未实现、已从 config 移除。** 启发式 AI 加上路权让行（§8）后，1000 局受阻回合占比 0.1%、零卡死；以后若真人/LLM 试玩出现大量堵死胡同口，再实现并重标密度。

## 2. 角色、体力与移动

### 2.1 体力 【定】U4e ＋【沿用】400

- 体力初值 = 上限。取值按**玩家座位的控制通道**选：

  | 通道 | 初值 / 上限 |
  |---|---|
  | `manual` 亲手玩 | 400 |
  | `prompt` 用语言指挥自己的 agent | 400 |
  | `script` 自写脚本 | 400 |

  三项初值都是 400，之后按试玩和仿真分别调。
- **同一局里四个角色的体力相同**（公平）【实现】：通道决定的是整局的取值，不是只给玩家。
- 宝箱回复的体力不超过上限，溢出部分丢弃。

### 2.2 体力消耗 【定】U4a

- **只有成功位移扣 1。** 其他情形一律扣 0：
  - 主动停留；
  - 撞墙或越界（引擎改为 STAY）；
  - 被角色挡住；
  - 同格冲突、对穿、环；
  - 四面受阻。
- **不设僵持兜底。**
- 体力为 0 时不能移动，意图强制改为 STAY。

### 2.3 失败与离场

- 位移结算后体力 = 0 且不在自己出口 → **失败**，立即离场。
- 第 `maxTurns`（600）回合结算后仍在场 → **失败**【沿用】。
- 达成或失败的角色离场，不再占格。

### 2.4 由 U4a 推出的后果（须知情）

- 堵人对双方都是零成本。规则层面的兜底只剩 `maxTurns`，僵局靠 AI 自己解开（§8 第 5 条）。
- 停留免费，所以局长可能拖向 600 回合。
- 阶段 1 仿真要监控三个指标：被挡回合占比、因 `maxTurns` 失败的比例、局长分布。

## 3. 宝物与计分

### 3.1 宝石 【定】U1

- 5 色：`red` 红、`yellow` 黄、`green` 绿、`blue` 蓝、`purple` 紫。每代每色 1 颗，**一代 = 5 颗**。
- 本代 5 颗全部被拾取（不论被谁）→ 同一回合第 7 阶段重生下一代。
- **最多重生 2 次**（共 3 代 15 颗）【沿用】。**阶段 1 结论：保持 2 次**（O3）——改成 3 次时人均宝石只从 3.06 涨到 3.10，因为体力先于宝石耗尽；改成 1 次则 84.6% 的局宝石被拿光（附录 B）。
- 重生位置：与初始撒点同一套算法，并且距每个在场角色 BFS ≥ **15**。当回合放不下 → 记 `gemRespawnDeferred`，下一回合再试（1000 局里从未发生）。

### 3.2 计分 【定】U1

```
score = Σ_c n_c  +  setBonus × min_c(n_c)  +  宝箱得分
setBonus = 5     // n_c = 该角色已拾取的 c 色宝石数
```

- 例：(红2, 黄2, 绿3, 蓝3, 紫1) → 11 + 5 × 1 = **16** ✓
- 另一种等价说法：每凑齐一套（五色各 1 颗），这一套按双倍计分。
- 理论上限：15 颗 + 5 × 3 套 + 宝箱 3 × 5 分 = 45。

### 3.3 宝箱 【定】SPEC-0.4（2026-11-11 用户裁定）

- 全场 1 个。开启固定 **+5 分**，不给体力（`pScore = 1`、`scoreRange = [5, 5]`）。结算仍先抽「分还是体力」再抽数值，随机流调用次数与旧规则相同。
- SPEC-0.3 及以前：50% → +1~5 分；50% → +25~50 体力（均匀分布，`chest` 随机流）。
- 第 t 回合被开启 → 最早在第 t+60 回合的第 7 阶段重生；最多重生 2 次。
- 重生位置距每个在场角色 BFS ≥ **30**，其余约束同撒点。

### 3.4 撒点算法 【实现】（源自 02b，改为本规格口径）

- **候选池**：主连通域内的地板，排除距出生点切比雪夫 ≤3、距出口切比雪夫 ≤2 的格。
- **开局**：5 颗宝石 + 1 个宝箱共 6 件，逐件做拒绝采样：
  - 与已选件的曼哈顿距离 ≥ 30；
  - 每件最多试 30 次，不成就整组重启，最多重启 4 次。
- **公平性**：对每个座位 i 求 `D_i = Σ_件 BFS(spawn_i, 件)`，要求 (max D − min D) / mean D ≤ **0.35**，不满足就重启。
- **兜底**：随机抽 64 整组，在满足公平性的组里取「最小两两距离」最大的一组；仍失败 → 记为 V7 失败，地图重掷。
- **重生时**：只放这次要重生的件，并额外满足距在场角色的 BFS 下限。实在放不下时，最小间距按 30 → 20 → 10 → 0 逐级放宽并记日志；**距角色的下限永不放宽。**

## 4. 回合结算（确定性硬约束）

`step(state, intents) → { state, events }` 是纯函数。回合号从 1 到 600。

| 阶段 | 内容 |
|---|---|
| 1 意图 | 每个在场角色提交一个 `N\|E\|S\|W\|STAY` |
| 2 合法化 | 目标是墙或越界，或体力为 0 → 改为 STAY（记 `bump` 事件，不扣体力） |
| 3 仲裁 | 见下方算法 |
| 4 位移 | 所有成功者同时更新坐标 |
| 5 体力 | 位移成功者 −1；体力 = 0 且不在自己出口 → 失败并离场 |
| 6 拾取 | 按座位 0→3：踩到宝石 → 计入该色；踩到宝箱 → 掷骰。第 5 阶段已失败者不参与（体力归零时踩着宝箱也不能续命）【沿用】 |
| 7 重生与终局 | 宝石全空且代数未满 → 重生；宝箱到期 → 重生；站在自己出口 → 达成并离场；若 turn = maxTurns → 其余在场者判失败；全员结算 → 本局结束；否则 turn + 1 |

**仲裁算法**【实现】：结果与座位顺序无关；两人或多人抢同格、对穿、环的处理沿用旧文档【沿用】。

```
movers = { i | dir_i ≠ STAY }，t_i = p_i + dir_i
① 同格冲突：目标为同一格 c 的 mover ≥ 2 个 → 这些人全部 blocked
② 环：在 movers 上建边 i→j（t_i = p_j 且 j ∈ movers）；任一环上的人（含长度 2 的对穿）全部 blocked
   （网格二着色，环长必为偶数，最小 4；没有 3 人环分支）
③ 迭代到不动点：t_i 被某个本回合不动的角色占据（STAY / blocked / 非 mover）→ i 也 blocked
④ 剩余 movers 同时位移（链式让位允许）
```

- **边界**：最后一步体力 1 → 0 正好踩上自己出口 → 达成（第 5 阶段不判失败，第 7 阶段判达成），剩余体力记 0。

## 5. 胜负与排名 【沿用】

**冠军排序**（逐条比较）：

1. 达成者 > 未达成者（未达成者不争冠军，只排名次）
2. 分数高者胜
3. 剩余体力多者胜
4. 达成回合早者胜
5. 仍相同则平局（并列冠军，UI 明示）

- **全员未达成**：冠军空缺。按 分数 → 剩余体力 → 移动步数少 排名次。
- **本局结束条件**：全部角色都已结算（达成或失败）。玩家结算后自动切到 4× 观战，可随时跳过。

## 7. AI agent 决策（LLM）

### 7.1 规划式 【沿用】

- LLM 输出 `{ targetType: "gem"|"chest"|"exit", target:{x,y}, reason }`，引擎用 BFS 执行逐步移动。
- 目标必须是当前存在的宝物，或者自己的出口。否则视为无效 → 降级到 L1（§7.6）。

### 7.2 节奏

- **基准重规划间隔 8 回合**【沿用】；降本时中盘最多放宽到 10。
- **终盘区**（每个 agent 自己判）：`stamina ≤ 1.3 × distToExit`，整数比较 `s*10 ≤ d*13`。
  - 终盘区内间隔为 6，不参与任何降本。
  - 【实现】这是终盘的唯一定义。旧文档里「最后 60 回合」「体力 ≤60」两种写法作废，因为运行时不知道一局还剩几回合。
- 事件触发即刻重规划，并重置基准计时。
- **计划完成**（到达目标）也立即重规划：计入调用池，不计入事件上限【实现】。

### 7.3 重规划事件（5 条）

| # | 事件 | 触发条件 | 类型 |
|---|---|---|---|
| ① | 目标失效 | 当前目标被**他人**拾取或开启 | 边沿 |
| ② | 宝物刷新 | 新一代宝石重生，或宝箱重生 | 边沿 |
| ③ | 路径受阻 | 有移动意图，但连续 2 回合未位移（STAY 不算）；成功位移后复位 | 边沿 |
| ④ | **体力告警**【定】U4c | 进入「体力不足以走到出口」状态（`stamina < distToExit`）时触发一次重规划。状态持续期间，观察里 `lowStamina = true`，HUD 常亮红色；直到状态解除（例如开箱回了体力）。解除后再次进入，可再次触发 | 持续状态，进入时调用一次 |
| ⑥ | 对手进入视野 | 任一对手从视野外变为视野内 | 边沿 |

- 已删除：⑤「视野内出现自己没有的颜色」（U4d）；⑦「冲刺窗口」（旧文档已删）。保留原编号，便于对照旧文档。
- 每个 agent 每局事件上限 **10** 次，冷却 ≥ **3** 回合（同一 agent 的任意两次事件之间）【沿用】。超过上限或在冷却中的事件不调用 LLM，只记录。

### 7.4 调用预算 【沿用】数值待阶段 3 用 mock 重测

- 每局总量硬上限 **360**。
- 常态池 **240** / 终盘池 **120**，物理隔离。每个 agent 常态软上限 **60**；终盘额度为每人每局 **10** 次，重入终盘不重置。
- 事件调用计入常态池。池子耗尽 → 该 agent 转启发式（§8）。
- 提示词托管的玩家算第 4 个 agent，共用同一套池子。

### 7.5 生效时序 【实现】（SPEC-0.3 起零缓冲，2026-11-10）

- 帧号：`frame(0)` = 开局（尚未行动）；`frame(k)` = 第 k 回合结算后的局面（非终局时内部 `state.turn = k + 1`）。
- 决策点基于 `frame(k)` 发请求，调度器**当场停下等回复**；回复合格后新计划驱动第 k+1 回合的**第一步**（`ai.planLatencyTurns = 0`）。首个决策点在 `frame(0)`，任何人行动之前。所有大模型座位同一规则；同一回合多个座位一起等，等最慢的。
- 超过 `timeoutMs`（本地代理 8000；中转按思考档位）→ repair 一次 → 仍失败降级；熔断（L3）立即解除等待。
- 每个决策点有编号 `dp`（修复重交沿用、`rev + 1`）；结果以事件流记录（applied / invalid / failed / stale / cancelled / guard / abandoned / lost / reached / queued / replaced / continued / interrupted，见 redesign §14 C5、C14）。零缓冲下 `stale` 应为 0。
- 被问到时可回 `{"keep":true}` 续走当前计划（目标 / then / abandonIf 原样保留，记 `continued`）；交同一目标也记 `continued`，换目标才记 `replaced`。规则正文如实列出何时会被问（含与目标无关的事件）与平局规则（分数 > 剩余体力 > 到达回合）。2026-11-11 起复盘里的「白跑」为净绕路（扣除顺路向出口的步数）。
- SPEC-0.4：目标被抢、宝石 / 宝箱刷新**必问**（不占每局事件次数；目标被抢下一回合就问；刷新遇 3 回合冷却则推迟到冷却结束，期间被别的原因问过就算问过）；对手接近 / 受阻 / 体力终盘仍受冷却与次数限制、不补问。额度充足时大模型座位不再由启发式代走。
- SPEC-0.4 等待动作：`{"targetType":"wait","turns":1–10}` 原地等；`{"targetType":"home","stopAt":1–3}` 走到离出口 stopAt 步处再等（最多 10 回合，不进出口）。原地等不耗体力；等满到期必问（`woken expired`，`then` 有下一个则接着走）；刷新叫醒必问（`woken refresh`，回 keep 接着等）；等待中其他事件与定期都不问；每局累计 ≤ 40 回合；剩余回合 ≤ 回家步数 + 2 时引擎改回出口（`guard cause time`）。配置 `ai.wait`。录像仍记原地不动，严格回放不变。
- 决策回包 / 提示词带「上次决策以来」：上一个决策点之后到本次的逐回合轨迹 + 上次决策的结果事件（与 MCP 同一个 `src/ai/decision-packet.js`）。
- 回放只读记录、不调模型，所以对局结果与倍速、网络快慢无关。内核里没有墙钟窗口，等待和超时看门狗放在内核外层。
- SPEC-0.2 及以前为 `L = 2`（第 t 回合请求、第 t+2 回合生效，期间沿用旧计划），只为旧配置保留。

### 7.6 降级链（对局绝不中断）【沿用】

| 级别 | 触发 | 行为 |
|---|---|---|
| L0 | 等待回复中 | 整局停在这一回合（零缓冲后不再「沿用旧计划先走」） |
| L1 | 没有有效计划 / 目标失效 / 预算耗尽 | 启发式（§8） |
| L2 | 超时 / JSON 不可解析 | repair 1 次（≤150 token），再失败转 L1 |
| L3 | 代理不可达 / 连续 3 次 5xx / 429 持续 | 本局全体改用启发式，HUD 提示 |

### 7.7 玩家自己的大模型：harness 【定】2026-11-06 批次 6

玩家座位接自己的模型时（05 模式 B），规划器按「agent harness」管理：一局一个会话，跨局有长期记忆。对手 AI（模拟 / 本地代理）不变。完整设计见 05 §7.6–§7.9，要点：

- **博弈事实表**（`codec.buildPayload`）：所有算术由引擎算好。每颗宝石 / 宝箱 `race[]` = 每个在场对手的 `dist`（他到这里）、`back`（这里到他出口）、`canReturn`（拿了还回得了家）、`needsColor`（是不是他凑套最缺的颜色），`lead` = 最近一个拿得起的对手步数 − 我的步数。每个对手 `distToExit`、`spare`（体力 − 到出口距离）、`heading`（近 6 回合在靠近的目标，最多 2 个）。
- **本局会话**（`harness.sessionText`）：每次请求的 user 消息前面带「本局到目前为止」：最近 8 条决策原样（触发、目标、理由 → 结局：拿到 / 被谁抢先几步、白跑几步 / 主动放弃 / 改主意 / 闸门 / 作废），更早的折成一行摘要；再加模型上次留给自己的 `memo`（≤ 300 字）。
- **决策契约 v2**：在 v1（`follow` / `deviation`）之上可选 `then`（≤ 2 个后续目标，拿到当前目标后引擎直接接着走，记 plan 行 `src: 'queue'`）、`abandonIf.rivalLeadBy`（有拿得起的对手比我近 ≥ k 步就放弃，引擎每回合检查，触发记 `src: 'abandon'` 并同回合重问，`why: 'abandon'`）、`memo`。写错的可选字段丢掉，不判整条不合格。自保闸门第一次改写某个计划时记 `src: 'guard'`。`queue` / `abandon` / `guard` 不算「一次决策」。
- **跨局经验**：每人每个模型（`服务商/模型`）一份，≤ 2000 字，存服务器（`memories` 表，迁移 v5；`/api/v1/memory`）。开局植入 system 提示词的一段；赛后由模型根据本局复盘自己整份重写（目标 1200 字），超长时让模型压缩。玩家可查看、编辑、清空、关掉。记录 `meta.players[].memoryHash` 只存哈希。
- **思考档位** `off / low / high`，默认 `low`，按服务商查表（`server/providers.mjs`，2026-11-06 真凭证实测）：HY4 只能关；Kimi K3、GLM 关不掉（「关」= `reasoning_effort: low`）。思考 token 另给预算（低 +3000、高 +7000），超时 45 / 75 / 150 秒。思考用光预算、答案为空时服务器自动用「关」档补问一次。记录 `meta.players[].thinking`。
- **确定性**：会话、动向历史、队列、放弃条件都只由观察与已生效的计划推出；记录照常严格回放。复盘时间线 `harness.timelineFromRecord` 由记录重放得到，与对局中给模型看的会话逐条一致（测试断言）。

## 8. 兜底启发式 AI 【实现】阶段 1 用仿真定参

输入是同一份观察（批次 6 起对手位置全公开）。启发式只把近身范围（R = 9）内的对手当障碍。每回合按下面顺序决策：

1. **回家**：`s*10 ≤ d_exit*13` → 进入 HOME。体力回到阈值以上时（例如开箱后）退出 HOME。（修正旧 lib「一旦回家不可逆」的问题。）
2. **候选**：在场宝石 + 宝箱。可负担条件：`s ≥ d(me,t) + ceil(1.3 × d(t,exit))`，即回程留 30% 余量（取旧 bench-match 口径）。
3. **价值**：
   - 宝石 `v = 1 + 5·Δsets + w_progress·[n_c == min]`；
   - 宝箱 `v = w_chest(s)`；SPEC-0.4 起宝箱只给分，`v = 宝箱分数（5）`，与宝石同口径（`scoring.chestFixedScore`）；
   - 评分 `v / (d + 1)`，平分时按 `(y, x)` 升序取。
4. **移动**：沿目标 BFS 距离场下降的方向走；有多个等价方向时，用 `ai` 随机流选（避免旧实现的方向偏置）。
5. **解锁**（U4a 之后必需；阶段 1 仿真暴露了两种对称死锁，规则据此改写）：有移动意图却连续 `unblockAfter = 2` 回合未位移时——
   - **路权**：体力低者先行，同体力座位号小者先行。双方只用公开信息（体力、座位）判定，结论必然一致，所以**只有一方改道**。旧写法「双方都把对方当墙重算」会让两人同时后退、又同时折回，在走廊里来回直到体力耗尽（实测 200 局里约 1% 的人次因此死亡）。
   - **堵路者就在最短路的下一格**：有路权 → 继续顶；无路权（或有路权但连续受阻 ≥ `yieldEscalateAfter = 6`，说明对方退无可退）→
     - 把视野内角色当墙重算，绕路比原路多出 ≤ `detourMaxExtra = 12` 步 → **承诺绕路**：这些避让格在 `detourCommitTurns = 12` 回合内一直当墙，防止走一步就折回原路；
     - 否则进入**让行模式**：每回合往远离对方的方向退一步，距离相同时优先不挡对方去它出口的那一格（拿不到对方目标，出口是最好的猜测）；对方不再处于「比我离目标更近」的位置即退出，最长 `yieldMaxTurns = 16` 回合；退无可退（死胡同）时立刻退出，继续顶，交给对方在 `yieldEscalateAfter` 后让。
   - **同格冲突**（两人隔一格抢同一格，§4 规则下双方都不动）：目标格旁有可见角色时，按 `yieldPct = 50%` 掷币让一回合。旧写法在这种情形下会永远僵持到 maxTurns（实测 20 局里 3 人）。
6. **无目标** → HOME。

权重 `w_*` 与解锁参数写在 config 里（§14）。阶段 1 结果：1000 局 4000 人次到达率 100%，无体力耗尽、无回合上限失败，受阻回合占比 0.1%（附录 B）。

## 9. 玩家控制通道

### 9.1 手动 【实现】

- 每回合等待玩家输入，**无超时**；AI 计划在后台并行预取。
- 按住方向键时按当前倍速的节拍连续走。
- 方向映射（屏幕方向 vs 网格方向）在灰盒阶段做 A/B 对比【待定】。

### 9.2 脚本 · 统一编程接口 v2（2026-11-03）【实现】

完整接口见 `docs/07-脚本编程接口.md`。要点：

- **人和 agent 同一套**：通用 agent 是「用写代码的方式玩的玩家」，与人用同一接口、同一份公开信息（§6.1）、同一套规则与预算。脚本写一次管一整局，**任意座位**都能用，和手打 / 接入大模型 / 电脑混排同场。
- **接口**：可选 `init(ctx, api)`（开局一次）+ 必须 `decide(obs, api)` → `'N'|'E'|'S'|'W'|'STAY'` 或 `{move, intent}`；模块变量整局保留。`ctx` = 整图、四个出生点、四个出口、本规格规则（无种子、无各座位模式）；`obs` 另附上一回合公开事件 `obs.events`。
- **api**：距离场 / 最短步不限次数（按计算预算计）；`api.sim.step` 单回合规则推演（底层真 `step()`，开箱只给概率分支、刷新只给标记、视野外对手需自行假设）；`api.random` 可复现（`Math.random` 同流）；`log` / `budget` / `elapsed`。v1 的 `obs.state` / `setState(≤16KB)` / `distance` / `shortestStep` 照常。
- **预算（方案 C）**：`init` 2000 ms；每回合 50 ms + 时间银行（≤ 5000 ms）；超支当回合作废、沿最后的 intent 兜底（无 intent 回家）；卡死（可用 + 400 ms）重建并重新 init，3 次 → 自动回家。评测（`maze-eval` / 整局试跑）默认只统计不打断，结果逐字节可复现。预算常量在 `src/player/runtime/budget.js`，不进 cfg（配置哈希不变）。
- **降级**：累计 5 次软异常（返回值无效）→ L1 自动回家；连续 10 次硬异常（抛错 / 卡死）→ 玩家座位 L2 切回手动，其他座位 L1。撞墙是正常玩法，不计数。
- **运行环境**：浏览器模块 Worker（实时对局）、Node `vm`（命令行评测）、浏览器评测 Worker（整局试跑）共用 `src/player/runtime/*`。
- **诚实边界**：沙箱是防误触 + 可观测 + 可复盘，不是安全隔离；不用 `eval` / `new Function`（Blob 模块 Worker，CSP `worker-src blob:`，由服务器响应头下发）。
- 原「每回合 ≤ 8 次寻路、只能查公开目标」的限制取消：脚本本来就拿到整张地形，自己写 BFS 就能绕过，限制挡不住信息、只为难写脚本的人。

### 9.3 提示词托管 【沿用】· 2026-11-02 起界面不再提供

- 设置页只剩「自己手打 / 编写 Agent 脚本 / 接入大模型」三种；内核与服务器仍认 `prompt`，旧记录照常校验，存档里的 `prompt` 自动改回手打。
- 与 AI agent **完全同构**：同一观察、同一模板骨架、同一节奏、同一预算池。
- 玩家只能改「人格 / 策略」段，截断到 2000 字符；不能改观察注入部分。

### 9.4 玩家 AI 代打（U6）【B 已实现（M1）· A 设计中】

- 两种方式：**A 外部 Agent**：卷轴提示词；对局在服务器上跑（服务器宿主），玩家电脑上的 Agent 通过服务器的 Agent 网关 `/agent/v1/*` 取局面、交决策，浏览器只观战。**B 自带模型**：对局在客户端跑；玩家的 API key 交给服务器保管，调用经服务器中转，谁用谁付。两者都复用 §7 的规划 agent：同一观察、同一决策点、同一生效时序，所以对局结果与 AI 思考快慢无关。
- 决策契约在 §7.1 基础上加 `follow`（yes / partial / override）、`deviation`、`memo`；自主度三档（自主 / 结合 / 严格），严格档的 `override` 判为不合格。M1 实现了 `follow` / `deviation`（`memo` 随模式 A 落地）。
- B 的规则条款（M1）：玩家通道 `playerMode: 'byok'`，体力同其他通道 400；自保闸门默认开（回不了出口的目标改为回家，记「引擎安全覆盖」，不算偏离），可关；每局调用上限可设（含修复），到上限后由启发式接着打；生效时目标已被别人拿走的合格计划记「过期」，不算不合格；玩家可随时接管 / 交还 / 换启发式代打，严格回放只读意图，不受影响。
- 完整设计、协议、提示词草案、分期与验收：`docs/05-玩家AI代打设计.md`；服务器、多端与数据记录：`docs/06-多端与服务器架构.md`（M1 实现说明 §13.2）。

## 12. 确定性与记录 【实现】

- **随机数**：用 mulberry32；具名随机流 k：1 迷宫、2 撒点与重生、3 宝箱、4 AI。
  - 迷宫：`subSeed(subSeed(seed, 1), attempt)`；撒点与重生：`subSeed(subSeed(seed, 2), attempt)`（重掷后撒点流也跟着换）；宝箱：`subSeed(seed, 3)`；座位 i 的启发式 AI：`subSeed(subSeed(seed, 4), i)`。
  - 字符串种子先用 FNV-1a 转成 32 位整数。
  - 撒点流与宝箱流的内部状态存进对局状态，所以重生结果进 `stateHash`、能被严格回放复现。
- **时间与随机 API 的使用范围**：
  - `Math.random` 只允许出现在 `rng.js`（仅 `freshSeed()` 给 UI 生成新种子用）；`Date.now` / `performance.now` 只允许出现在 `app/clock.js`。
  - `core/`、`ai/`、`record/`、`sim/`、`config/` 不读时钟、不用计时器。`tools/lint-determinism.mjs` 扫描这些目录，`npm test` 先跑它。
- **数值**：状态全部为整数；比例比较一律用整数乘法（如 `s*10 ≤ d*13`）。
- **哈希**：`stateHash` 对规范化 JSON（键排序）的动态状态做 FNV-1a 32 位哈希；静态地图单独算一次 `mapHash`；`configHash` 对整份 config 计算。
- **记录格式（JSONL，`RECORD_VERSION = 3`；回放器同时接受 v1 / v2）**【实现】紧凑格式：
  - `{"t":"meta","v":3,"rulesVersion","seed","configHash","mapHash","attempts","seats"?}`——`seats` 是各座位的控制通道标签（`manual` / `script` / `prompt-mock` / `mock:setHunter` / `proxy:chest` / `heuristic` …），只作复盘说明
  - `{"t":"turn","n":12,"i":"NE.-","h":"a1b2c3d4"}`——`i` 每座位一个字符：`N E S W`，`.` = STAY（无法识别的意图也记 `.`），`-` = 不在场；`h` = 本回合结算后的 `stateHash`
  - `{"t":"plan","n":13,"seat":1,"req":13,"src":"llm","dp":5,"rev"?,"plan":{targetType,target,reason}}`——LLM / 提示词托管的计划**生效**行。`n` = 生效回合，`req` = 发起回合（SPEC-0.3 零缓冲下 `n = req`），`src` ∈ `llm` / `llm-repair` / `invalid` / `stale` / `failed` / `queue` / `guard` / `abandon`，`dp` / `rev` = 决策点编号与修复版本（v3）。严格回放不读它，只供复盘
  - `{"t":"outcome","seat":1,"dp":5,"type":"lost","k":20,...}`——v3 新增：所有大模型座位的决策结果事件（`k` = 帧号，原因参数见 redesign §14 C5）。严格回放不读它，服务器只做形状检查
  - `{"t":"end","n":388,"ranking":[{seat,place,champion,status,score,stamina}]}`
  - 事件与决策帧不落盘（可由回放重算：`src/record/frame-replay.js` 由「严格回放 + 逐回合 observe」重建任意座位的帧，与对局中实时帧逐字段一致）。
- **严格回放**：只读记录，不调用任何决策者；先校验 `configHash` 与 `mapHash`，再逐回合比对哈希，不一致立即抛 `ReplayMismatch`（带回合号）。
- **存储**：浏览器端存 IndexedDB（最近 20 局）；本地代理可选落盘。【U7 后】服务器是对战数据的权威存档：服务器宿主的对局直接入库；客户端宿主的对局结束后上传，服务器用同一内核严格回放校验（`verified` / `mismatch`）；离线对局联网后补传。IndexedDB 降为本地缓存和离线队列。详见 06 §6。**S0 已实现**（2026-10-29）：游客令牌、`POST /api/v1/matches` 上传 + 校验、离线补传、设置页「我的战绩」，实现说明见 06 §13.1。

## 附录 C · 视野规则对比实验（2026-11-06，`npm run exp:vision`）

**读数（客观观察，供拍板参考）**：
1. **XS 上各规则没有差别**：19×19 的视野基本覆盖 16×16 全图，本来就是明牌。
2. **R4 风险成立**：现行规则的遭遇回合占比 S 53%、M 17%、L 10.5%、XL 7.4%。XL 低于原定 10% 的门槛，L 贴线。规则对物理遭遇影响很小（信息多了，玩家略微躲开彼此）。
3. **信息越多，白跑越少**：「预判对手」的白跑步数，从 A 到 B 依次是 S −11%、M −16%、L −12%、XL −9%。延迟 3 回合和雷达 15 回合接近全公开，延迟 10 回合接近现行规则。只看距离的启发式白跑最多（M 38、XL 72 步）。即使在现行规则下，用体力差做推断也比启发式少白跑约 20%。
4. **争抢没有消失**：每局约 5 次，全公开只比现行少约 0.3 次。「位置全透明 → 博弈消失」这个原先的担心，在这个指标上没有被证实。
5. **运气占比都很低**（|r| ≤ 0.16）；S、M 上全公开比现行略低（0.10 → 0.01，0.11 → −0.03），但在噪声范围内。
6. **技巧分噪声大**（40 局下，冠军率 1 局 = 2.5 个百分点）：XS +1.6 分，S、M +0.3 – 0.75，L 上全公开 +0.45、现行 +0.07，XL 各规则都接近 0。说明这个参考脚本的推断在大图上帮助有限，不能说明规则本身。
