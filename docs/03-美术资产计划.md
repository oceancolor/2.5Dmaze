## 一、风格定义

### 1.1 风格一句话

> **低饱和马卡龙奶油色地面 + 压暗一档的 art deco 暖灰墙 + 单方向固定光；四只高饱和小机器人是画面里唯一的彩色。**
> 三层明度结构：地面最浅（大面积）→ 墙中等 → 角色高饱和。场景做"静"，角色做"闹"。

> ⚠️ v1.0 的"墙也是浅色马卡龙"被否掉了 —— 它与需求 #7 的明度差 ≥40 直接冲突。**墙必须比地压暗一档**，这是需求的硬约束，优先于风格直觉。

#### 场景饱和度分离（`V21` 的更强形式 —— 我把创意总监的"只管装饰"推广成"整个场景"）

创意总监的判据只约束装饰。**但核算后发现整个非角色场景本来就都 ≤0.25** —— 所以这条可以写成一条**更通用、更难被绕过**的断言：

| 类 | 主色 HSV S 实测 | 约束 |
|---|---|---|
| 地面 F1–F4 | 0.031 – 0.082 | ≤ **0.25** |
| 装饰 D1–D3 | 0.115 – 0.153 | ≤ **0.25** |
| 墙 A 三档 | 0.162 / 0.182 / **0.233** | ≤ **0.25** |
| 墙 B 三档 | 0.127 / 0.184 / 0.195 | ≤ **0.25** |
| **`TIL_EXIT_*`** | = 角色色（0.71–1.00） | **不校验**（它是角色色，本就该跳） |
| **`ACT_*`（角色）** | **0.71 / 0.84 / 0.93 / 1.00** | ≥ **0.55** |

```
最小间隔 = min(ACT) 0.71 − max(TIL_非出口) 0.233 = 0.477  ≥ 0.30 ✅
```

> **为什么推广成"整个场景"更好**：只卡装饰的话，有人把**墙**画成高饱和马卡龙（这完全符合用户的字面风格要求！）就会绕过判据 —— 而那时"装饰不抢眼"这条其实已经被破了，只是没人测墙。
> 卡"所有非出口 `TIL_*` ≤0.25 且所有 `ACT_*` ≥0.55"则堵住了这个口子，**且当前全表已合规，0 改色成本**。
>
> **通则（创意总监抽象）**：**一条判据如果只约束"我在想的那一条路径"，它就留了一个我没在想的路径的口子。判据的约束对象应按「能造成同一种破坏的所有东西」来定，而不是按「我刚发现问题的那个东西」来定。**
> → 与 `N11`（描边不是装饰，是承载判据的机制）同一族：**N11 给机制定性，V21 推广给约束对象定范围。**

> **为什么还要单列"`N18` 间隔"**（qa-lead 补充，我认同）：只卡单侧（≤0.25 / ≥0.55）**守不住间隔** —— 角色降到 0.56、场景升到 0.27，两侧都合规但间隔只剩 0.29。
> **单侧值管"各自别越界"，间隔值管"两者别靠近"。** 这是两种不同的破坏方式，需要两条判据。

**选取原则（三条，按优先级）**

1. **与地面双通道分离**：地面 L\*≈85–92 / S≤0.12；角色 L\*44–77 / S≥0.70。明度差 ≥13、彩度差 ≥55 个百分点 —— 任一通道失效另一个仍成立。

3. **玩家独占最高彩度 + 独占光环**：`#FFD84D` 暖金在整张场景色板里不存在，是**玩家唯一性的第一通道**。

**为什么在出口上也读得出**：出口 = 地面圆盘，2px 白色内描边 + 1px `#3B362F` 外描边与任何地面变体隔离；出口色 = 角色色**同一常量**，不经 tint，误差 0。

#### 3.2.2 默认档 **2×**（主理人提问，我确认同意 —— 但带三条美术侧前提）

> 主理人：「默认档从 1× 改成 2×，你同不同意？若反对（比如 2× 下每步 100ms，跳跃根本看不清）→ 退回 180 + 默认 1×。」

**我的答复：同意。** 但先把 2× 下到底损失了什么说清楚 —— 这是美术侧该给的数：

| 项 | 1×（观察档） | **2×（默认档）** | 4× |
|---|---|---|---|
| 每步墙钟 | 200 ms | **100 ms** | 50 ms |
| 6 拍序列每拍 | 33.3 ms（30 fps） | **16.7 ms（= 1 渲染帧/拍，60 fps 满帧）** | 8.3 ms（2 拍/帧） |
| **hop 的 squash-stretch 弧线** | ✅ 读得出"跳" | ⚠ **读不出形状，只剩"移动了"** | ❌ 无 |
| **"谁在动"** | ✅ | ✅ **不受影响** | ✅ |

**关键判断**：2× 下丢的是**动作的形状**（squash-stretch 弧线），**不是身份**。而 400 步的竞速里，默认档要的是**吞吐量**不是"把每一步都看清"—— 玩家在看移动**模式**，不是在看每一步的弧线。所以这个 trade 是对的。

**三条前提（缺一不可，请写进判据）：**

| # | 前提 |
|---|---|
| 1 | **1× 必须保留为观察档。** 我的 ~180ms 节奏下限守的是**这一档** —— 2× 不需要它，1× 需要。取消 1× 等于让"读得出跳"这个能力无处安放 |
| 2 | 🔴 **2× 下"谁在动"由颜色 + 描边承担，不由动作形状承担。** → **`V15`（饱和度差 ≥0.55 + 描边 ≥5:1）与 `V21`（饱和度分离）从"补偿机制"升级为"默认档的主要机制"，判据等级不得降为 warn**，且不得以"风格统一"为由去掉描边（qa 已固化） |
| 3 | **光环脉动按 wall clock，不随倍速档缩放。** 玩家光环脉动周期 1.6s、宝石悬浮 4 帧 —— 若跟随倍速，4× 下光环会闪成 0.4s，读成"警告"而不是"身份标识" |

**6 拍这个拍数在 2× 下正好满帧**（每拍 = 1 渲染帧 = 60fps），说明拍数选对了 —— 若只有 4 拍，2× 下是 25ms/拍 = 1.5 帧，**会出现"有的拍显示 1 帧、有的 2 帧"的不均**。这是 ①' 序列方案的一个意外收益。

> **架构担心的"砍动画凑时长"仍不成立**：我没减帧、没减拍数，反而把拍数 4→6。只是节拍 62.5ms → 30ms —— 同一套动作，更快也更顺。

**①' 的序列（6 拍复用 4 张 + 复用 IDLE 首帧 → 0 新增 sprite）**

```
MOVE seq  = [ MOVE_00, MOVE_01, MOVE_02, MOVE_03, MOVE_00, IDLE_00 ]
拍 含 义  =   蓄力压缩   起跳拉伸   腾空最高   下落    落地压缩   回正
时 长     =  250 ms / 6 = 41.7 ms/拍（24 fps）
```

| 复用 | 理由 |
|---|---|
| 起跳压缩 = 落地压缩 → 同一张 `MOVE_00` | 两者都是 squash 姿态（机身压扁、腿弯曲），卡通跳本就对称复用 |
| 回正 = 标准站姿 → 复用 `IDLE_00` | IDLE 首帧即中性站姿，直接接回 IDLE 循环无跳变 |

> **为什么不直接采纳架构的 ①（实画 6 帧）**：① 与 ①' 的**观感差别只有两处**（落地压缩、回正），而①要多付 16 sprite / 25 KB / **tint 内存 +0.39 MB**（余量从 21% 压到 5.6%）。
> 先上 ①'（0 成本）；**若灰盒实测"落地那一拍看不出压扁"**，再补 2 张独立帧走 ① —— 预算我已核过，随时可加，不会卡。

**非均匀节奏（可选，同为 0 成本）**：`hold = [2,1,1,1,1,2]` → 蓄力 83ms / 腾空段 125ms / 回正 83ms。更符合 squash-stretch 的 weighting（蓄力与回弹慢、腾空快）。需动画层支持 per-frame hold。

**其余时长我核过的意见**

| 键 | 架构拟值 | 我的终稿 |
|---|---|---|
| `motion.moveMs` | 250 | **200**。低于 ~180ms，56px 角色的单格移动会读成"滑行/抖动"而不是"跳" —— 200 越过下限且留余量，250 无额外收益（详见上方裁定表） |
| `bumpMs` | 180 | ✅ 认同。BLOCK 2 帧 ÷180 = 90ms/帧（11fps）—— **撞击本来就该顿**，不需要顺 |
| `pickMs` | 300 | ⚠ **AI 侧偏低**：AI PICK 只有 2 帧 → 150ms/帧 = **6.7 fps**，是全场最低。若灰盒觉得"看不出在拾取"，**优先加 1 帧（+4 sprite / +6 KB）而不是延到 400ms**（延时会拖慢回合节奏）。玩家侧 3 帧 ÷300 = 10 fps，勉强够 |
| `endMs` | 600 | ✅ 认同时长，但 **DEAD 不应靠 2 帧硬切**：下沉 4px + 去饱和 60% 交给动画层做 tween（`600ms` 内插值），2 张 sprite 只作首尾关键帧。**0 sprite 成本** |

### 3.12 遮挡与 X 光轮廓（架构已算过，遮挡是真的）

**几何核算（架构给的数）**：前排墙 tile(11,10) 剪影落在世界 `y ∈ [320,368]`；角色身体 `y ∈ [280,336]` → **重叠 `y ∈ [320,336]` = 遮挡 16px = 角色 56px 的 29%**。

#### 3.12.1 遮的是哪一段（v1.4 · 回答创意总监的硬条件）

> 创意总监的判据：**不看 29% 这个数，看位置。** 遮下半身 → xray 默认关；遮到头或颜色主体 → xray 必须默认开。

**落点核算**（角色在 tile(10,10)，前排墙在 tile(11,10) —— 这是**最大**遮挡，更远的墙遮挡更少）：

| 部位 | 世界 y | sprite y | 是否被遮 |
|---|---|---|---|
| 头（含天线） | 280–304 | **0–24** | ❌ 不遮 |
| 躯干（**身份色最大连续面积**） | 304–322 | **24–42** | ❌ 不遮（仅最下 2px 擦边） |
| 腿 / 脚 | 322–336 | **42–56** | ✅ **被遮（16px）** |
| 前排墙剪影 | **320–368** | — | — |

**结论：遮的是「腿 + 脚」（sprite `y ∈ [40,56]`），头部与躯干完全暴露。**

**几何保底证明（不是估算，是不等式）**

```
合法前排墙的最小 C_y = 352（相邻格） → 墙顶世界 y = 352 − 32 = 320
角色头部最低点（= 躯干顶）世界 y = 280 + 24 = 304
304 < 320  →  恒差 16px
```
遮到头需要 `C_y ≤ 336`，即墙落在角色**自己格**（角色站地面，不可能）或**身后格**（绘制序在前，不遮挡）。
→ **"前排墙遮住角色头部"在数学上不可能发生。** 角色上部 **40px / 56px = 71%** 是绝对安全区。

**→ 按创意总监的判据：遮的是下半身 → `render.xrayOutline` 维持默认 `false` ✅，本条结案。**

#### 3.12.2 新增切图硬约束：**腿部高度 ≤ 16px**（V20）

> ⚠️ 这条不是审美建议，是 **3.12.1 结论成立的前提**。
> 若把机器人画成"大长腿"（腿 >16px），躯干下沿就会落进遮挡区 —— 而躯干是**身份色的最大连续面积**，那就变成"遮住了身份"，xray 必须默认开。
> **腿高 ≤16px 保证了「29% 遮的是脚，不是身份」。** 当前设计（腿 14px）合规 ✅。

| 项 | 规格 |
|---|---|
| config | **`render.xrayOutline`**，默认 **`false`**（v1.4 确认不动） |
| 触发改默认的唯一条件 | 若 V20 的"腿高 ≤16px"被破坏 → 本条默认值**必须改为 `true`**，不能留给玩家自己开 |
| 做法 | 角色被墙遮挡时，把角色轮廓以 **1px 角色色（alpha 0.9）** 叠画在墙之上 |

| 优先级 | **P1**，可延后 |

## 五、变体策略与分布（抗 16384 格重复疲劳）

**核心思路：大块给秩序（art deco 要对称节奏），小块给随机（抗重复）。变体总数锁死 12，不随地图规模增长。**

| 层 | 单元 | 规则 | 变体数 |
|---|---|---|---|
| 地面主色 | **chunk 8×8**（架构定稿；16×16 = 256 chunk） | `hueIdx = (cx + 2*cy) % 4` → F1–F4；**F5（砖纹）按格 hash 以 8% 概率替换**，用于打破大色块的单调 | 5 |
| 装饰 | 单格 | `(hash(gx,gy) & 0xFFFF) / 65536 < 0.15` → 放 1 个，`decoIdx = hash2 % 3`；**出口格及其 2 格邻域、出生点 3 格邻域禁用** | 3 |
| 墙体 | 单格 | `wallIdx = hash(gx,gy) % 4`；**墙角（两侧临空）强制用转角柱头变体** → art deco 转角节奏 | 4 |
| **合计** | | | **12** ✅ |

**hash 函数**（给主程序，确定性、无状态）：
```
h = (gx*73856093) ^ (gy*19349663);  h = (h ^ (h>>>13)) * 1274126177;  return (h ^ (h>>>16)) >>> 0
```
取模用 `h % N`；密度判定用 `(h & 0xFFFF) / 65536 < 0.15`。

### 5.1 装饰层：**烘焙进 chunk 静态层**（v1.4 定稿）

> ⚠️ **v1.4 推翻我自己 v1.3 的结论**。v1.3 我写的是「运行时叠加 + zoom<1.0 不画」，理由是"烘焙会把变体炸到 24"。
> **那个理由是把「烘焙进 chunk 位图」和「预组合成 atlas 新 sprite」混为一谈了** —— 这是两件完全不同的事（见下表）。我核过 drawOps 后确认：**每帧叠加必然打穿 P2，烘焙是唯一可行路径。**

| 项 | 决定 |
|---|---|
| **实现方式** | **烘焙进 chunk 静态层位图**（chunk 烘焙期每装饰格多 1 次 `drawImage`），运行时 **0 drawOp** |
| **绝对禁止** | **预组合成"地面×装饰"的新 atlas sprite** → atlas tile sprite 12 → **24**，直接违反 N01 |
| **密度上限** | **15% 的地面格**，**烘焙期**读 `render.decor.density` |
| ~~zoom 门控~~ | **取消**（理由见下） |
| **降级** | **无运行时降级函数**（运行时 0 drawOp，没有东西可降）。`density` 是**烘焙期参数**，改动需 chunk 缓存失效重烘 |
| **P24** | **不需要运行时降级路径** —— 装饰的降级发生在烘焙期，不在绘制循环 |

**为什么每帧叠加不可行**（v1.4 修正了我自己的估算）

```
等距晶格密度：基向量 v_gx = (32,16)、v_gy = (−32,16) → |det| = 1024 px²/格
屏内格数 @1080p zoom 1.0 = 1920 × 1080 / 1024 ≈ 2025 格   ← v1.3 我写"约 800 格"，错
装饰格 = 2025 × 15% ≈ 300 格 → 每帧叠加 = 约 300 drawOps
```
> ⚠️ **v1.3 / 给 qa 的 N12 里写的"约 120 drawOps"是错的**（我低估了屏内格数 2.5 倍）。正确值 **≈300**，比 P2 的 80 高出近 4 倍。
> 结论方向不变、只会更强：**每帧叠加在任何密度下都不可行**，烘焙是唯一路径。

**⚠️ 关键区分：「烘焙进 chunk 位图」≠「预组合成地面变体」**（qa-lead N12 正在守这一条）

| | **烘焙进 chunk 位图 ✅（选）** | 预组合成新 sprite ❌（禁） |
|---|---|---|
| atlas 里 tile sprite 数 | **12（不变）** | **24** → N01 fail |
| 图集尺寸 | 256×256（不变） | 需扩到 384×256 |
| 运行时 drawOp | 0 | 0 |
| 组合发生在 | **运行时一次性**，在 chunk canvas 上（`drawImage` 两次） | **构建期**，在 atlas 里（生成新文件） |
| 变体计数（需求 #7） | 12 ✅ | **24 ❌** |

**为什么取消 zoom 门控**

zoom 门控原本是为了省那 120 drawOps —— **烘焙后没有 drawOp 可省，门控就失去意义了**。
且烘焙进 chunk 后，缩小视图时装饰像素随位图一起被缩放，**绘制期无法剔除**（除非按 zoom 档各烘一套 → chunk 缓存内存 +41%：35.6 → 50.3 MB，不划算）。

> 装饰在最小档的实际形态：11×3 px、alpha ≤0.28 的斑块，落在 15×7 px 的地块上，占 15% 的格子。
> **不影响 N05**：不干扰 16px 屏幕空间标记（尺寸差一个量级）。
> **不影响 N03**：复合后与墙顶 ΔV 仍 ≥41（缩小只会让装饰与地面进一步平均，不会更暗）。

**回退开关**：`render.decor.density = 0` 完全关闭（烘焙期生效，需重烘 chunk）。
~~**可选增强**：chunk 缓存按 zoomTier 分档~~ → **v1.4 不需要了**，见下。

#### 5.1.1 zoom 门控的最终落点（架构的 overview 方案帮我免费达成了）

架构指出：zoom **0.234 全图档不走 chunk**，走一张预烘焙的 **`OverviewCache`** 位图（1918×962，7.38 MiB，1 次 drawImage）。
→ **装饰的 zoom 分布因此自动成立，且 0 成本**：

| zoom 档 | 走的位图 | 装饰 |
|---|---|---|
| **1.0** | chunk（512×272） | ✅ 有（烘焙期叠加） |
| **0.6** | 同上，缩放绘制 | ✅ 有（~7×2px，架构说"看得见而且更好看"，同意） |
| **0.234** | **`OverviewCache`（另烤一张）** | ❌ **无** —— 天然达成我原本想要的"最小档不画" |

**⚠️ 但这条必须显式写进烘焙规格**（否则极易漏）：
> **`OverviewCache` 烘焙时必须跳过装饰层。**
> 它不是"恰好没有装饰"，是"必须不要装饰" —— 若哪天有人改成"overview 从 chunk 缩略图拼"，最小档就会长出装饰，**与设计意图完全相反**，而且那时没人会发现。

| config 键 | 值 | 用途 |
|---|---|---|
| `render.overview.excludeDecor` | **`true`** | overview 位图烘焙跳过 `TIL_DECO` |

**我不出额外资产**：overview 用同一套 tile sprite 在 0.234 缩放下直接烤，无需美术侧新增产出。已向 qa 确认 `L16`（最小档 ≥30fps）所需的一次性烘焙形态**本图集支持**。

**单格视觉组合数**：地面 5 × (装饰 3 + 无装饰 1) = **20 种地面外观** + 4 种墙体外观 = 24 种。在 16384 格上足够抗重复。

### 6.1 命名

格式：`<类别>_<名称>_<朝向>_<帧>.png`

| 字段 | 取值 |
|---|---|
| 类别 | `TIL` 地形/墙体/装饰/出口 · `ACT` 角色 · `PRP` 道具 · `UIX` UI |

| 朝向 | `n` / `e` / `s` / `w`；无朝向用 `na` |
| 帧 | `00`–`07` |
