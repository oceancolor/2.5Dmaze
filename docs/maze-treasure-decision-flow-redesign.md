## 1. 问题陈述

### 1.1 现状机制（实测）

- 决策点由事件驱动触发，`why` 包括 `start` / `complete` / `sighted` / `abandon` / `targetLost` / `interval` / `blocked` / `refresh`，**非固定周期**。
- 第 8–17 局共 486 回合、约 70 次决策 → 平均约 7 回合一次；单局 3–9 次。
- 决策点返回 `turn = n` 的**单帧快照**；决定在 **n+2 回合生效**，期间引擎按旧计划走。
- `maze_observe` 原样返回该旧快照，不刷新目标表。
- 引擎内部已有逐回合数据（`sched.toJSONL()` + 逐回合 `stateHash` 严格回放校验），`abandonIf` 也是引擎每回合检查，但这些数据未对 Agent 暴露。

### 1.2 三个核心问题

1. **信息不同源**：`events` 显示目标已被拿走 / 新一代已刷新，`targets` 仍是旧表。玩家被迫用 `abandonIf=0` 零步重评、或提交旧坐标 hack 出一次重评。
2. **两回合延迟窗口**：生效时目标已消失 → 作废；负优目标当跳板 → 作废；远目标 `dist+back > 体力` → 被引擎安全覆盖「改回家」，白丢一次决策。
3. **不确定性来源错位**：Agent 大量精力用于补信息差，而非博弈推理。17 局里最有价值的策略经验过半属于接口规避（不提交已消失目标、算 `dist+back` 防安全覆盖、零步重评等刷新、不假设 `exit` 可重问）。

### 1.3 证据表

| 局 / 回合 | 现象 |
|---|---|
| 第 15 局 | 3 次决策、0 白跑、0 作废、开箱 +4 分，仍因 `exit` 提前结算被对手 10 分反超 |
| 第 16 局 T25 | 负优蓝石当重评跳板，生效时已被座位 3 拿走 → 作废 |
| 第 16 局 T33 | 紫石 `dist 9 + back 16 = 25 > 体力 22` → 引擎安全覆盖「体力不够，改回家」 |
| 第 9 局 T14 | 提交事件已确认消失的黄石 → 作废 |
| 第 12 局 T19 | `abandonIf` 触发，整条 `then` 队列（含锁定的 `exit`）中断 |
| 第 3 局 | 官方白跑 1 步，实际连续追箱投入 8 步，统计口径失真 |

## 2. 目标与非目标

**目标**

- 根治信息不同源与延迟窗口造成的作废 / 安全覆盖。
- 让玩家在每次决策时拥有「上一次决策执行结果」的完整时序上下文。
- 为真实逐帧回放提供逐回合数据源。
- 保持决策频率、承诺成本、`then` / `abandonIf` 语义不变。

**非目标**

- 不改成每回合决策（调用量与博弈深度代价过大，见 §3）。
- 本方案**不**处理 `exit` 终局性、契约与 schema 不一致、`why` 触发时机（见 §10）。
- 不调整计分、宝箱奖励、体力预算、地图生成（平衡性改动另案）。

## 3. 方案比选

| 方案 | 结论 | 理由 |
|---|---|---|
| A 每回合决策 + 立即生效 | 否决 | 决策点从约 70 次/10 局升到约 486 次；每回合可反悔 → 承诺成本消失，退化为逐格贪心路径优化，`lead` / `then` / `abandonIf` 失去意义 |
| B 每回合决策 + 保留 +2 延迟 | 否决 | 后提交能否撤销前一个、队列如何结算均未定义；作废率可能更高 |
| C 观测层 / 决策层分离 | **实现层采纳，呈现层不暴露** | 「逐回合单一数据源」是实现必需；但「在线/离线两类消费者」等概念对玩家过重，不写进规则文本 |
| D 本方案 | **选定** | 一条规则可写进 prompt；同时解决同源、生效、回放数据，调用量不涨 |

**关键判断**：现状存在两种不确定性——「手里的信息已过期」是接口缺陷，「押注之后对手怎么走」才是博弈。本方案抹掉前者、完整保留后者，使分数能够反映博弈推理能力，而非补信息差的能力。

## 4. 玩家侧规则（最终呈现）

> 每次轮到你决策时，会先给你一段「上次决定之后到现在的逐回合记录」，以及当前这一回合的完整局面与博弈事实表。你据此提交一个目标，它从下一回合起立即执行；直到下一次轮到你决策为止，不能中途改主意。

其余规则（计分、体力、出口、`then`、`abandonIf`）沿用现有文本。此规则文本应同步更新到设置页提示词与 `maze_new_game` 返回的规则说明。

## 5. 机制规格

### 5.1 三条主变更

| # | 变更 | 说明 |
|---|---|---|
| 1 | 事件驱动决策不变 | 决策点触发条件、`why` 枚举、平均间隔均不变；不新增决策点 |
| 2 | 回合帧拼接后一次性下发 | 引擎按回合采集 `TurnFrame`；下一个决策点把「自上次决策以来的全部帧」打包，连同 `frame(n)` 完整事实表一起返回 |
| 3 | 决策立即生效 | 基于 `frame(n)` 提交 → **T_n+1 起按新计划移动**，无额外缓冲回合 |

### 5.2 时序

| 回合 | 引擎 | Agent |
|---|---|---|
| T_a（上次决策点） | 产出 `frame(a)`，返回帧段 + 决策帧 | 提交 decision A |
| T_a+1 … T_n | 按计划 A 移动，逐回合产出帧；`abandonIf` 每回合检查 | 不参与、不提交 |
| T_n（本次决策点） | 唤醒；打包 `frame(a+1…n)`，附 `frame(n)` 完整事实表、上次计划的 `decisionOutcome` | 读帧段 → 分析 → 提交 decision B |
| T_n+1 起 | 立即按计划 B 移动 | — |

`abandonIf` 在 T_a+1…T_n 之间触发时，引擎插入决策点，切出「a+1…触发回合」帧段下发。事件驱动的稀疏性因此不变。

### 5.3 「立即生效」的精确定义（硬约束）

- 「立即」= **无 +2 缓冲**；T_n 状态已结算完毕，新计划自 T_n+1 第一步开始执行。
- 不是「提交当回合立刻到达目标」，仅指计划开始寻路执行。
- 生效后不再存在「生效时目标已不存在」的判定窗口，`void_targetGone` 应归零。
- `dist + back > 体力` 的**安全覆盖仍然保留**（`allowRisk=false` 自保闸门，与延迟无关），但因决策基准是最新帧，误触发应显著减少。
- `then` 队列语义不变：主目标拿到后依次自动执行，不再询问；队列目标消失时零成本跳过。

## 6. 数据模型 `TurnFrame`

每回合一条、append-only、不可变。

| 组 | 字段 | 说明 |
|---|---|---|
| 标识 | `turn`, `stateHash` | 沿用现有逐回合严格回放校验 |
| 状态 | `self`, `rivals[]`, `targets`, `facts` | `targets` = `gems[]` + `chest` + `race` / `lead` / `rivalsNearer` |
| 事件 | `events[]` | 本回合 pickup / chest / respawn / arrival / elimination |
| 计划 | `plan`, `decisionRef` | 当前生效计划（主目标 + `then` + `abandonIf`）、对应决策 id |
| 结果 | `decisionOutcome` | `applied` / `void_targetGone` / `safetyOverride` / `abandoned` / `contested` / `completed` + 原因参数 |

**硬约束 1（同源）**：`frame(n).targets` **必须**是 `frame(n).events` 应用**之后**的真实集合；同回合被拿走的目标不得出现在该帧 `targets` 中。仅做「帧拼接」而沿用「旧 targets + 附加 events」的构造方式，问题不会消失。

**硬约束 2（单一数据源）**：决策帧的完整事实表逐字段等于 `frame(n)`，不得单独构造快照。

## 7. 决策点回包结构

分三层下发，**不可**把原始完整帧逐条倒给 Agent。

| 层 | 内容 | 用途 |
|---|---|---|
| 轨迹层 | `frames[a+1…n]` 精简帧：`turn`、各方位置 / 体力 / 分数、`events[]` | 时序上下文、对手走位推演、逐帧回放 |
| 摘要层 | 关键事件按类型分组 + 上次计划的 `decisionOutcome` | 快速归因「上次押注对没对」 |
| 决策层 | `frame(n)` 完整版：`self`, `rivals[]`, `targets`, `facts`, `terrain` | 提交本次决策 |

体积控制要求：

- `terrain` 按 `originX` / `originY` 变化做 delta 或引用，不在每帧重复。
- 完整 `race` 表只在决策层给。
- 提供 `fields` 裁剪参数（供回放 / 复盘按需取）。
- 粗估：每帧完整版数 KB；平均 7 回合一包 → 每次十几 KB、一局约 100 KB 量级、10 局约 1 MB 原始 JSON。精简后轨迹层应显著低于此。

决策点回包新增字段（建议命名）：

| 字段 | 含义 |
|---|---|
| `snapshotTurn` | 本次决策基于哪一帧 |
| `effectiveTurn` | 计划从哪一回合起执行（= `snapshotTurn + 1`） |
| `framesSinceLastDecision` | 帧段（轨迹层 + 摘要层） |
| `lastDecisionOutcome` | 上次决策结果归因 |

## 8. 接口变更

| 类型 | 接口 | 变更 |
|---|---|---|
| 保持 | `maze_new_game`, `maze_query`, `maze_history` | 不变 |
| 保持契约 | `maze_decide.decision` | 结构不变：`targetType`, `target`, `reason`, `then[]`, `abandonIf{rivalLeadBy}`, `memo` |
| 修改 | `maze_decide` 返回值 | 决策点回包按 §7 扩展；**去掉 +2 生效** |
| 扩展 | `maze_observe` | 新增 `fresh: true` 取最新帧真实局面；默认行为保持不变（向后兼容） |
| 新增 | `maze_frames(gameId, from, to, fields?)` | 批量取帧，只读、可重复、**不推进对局** |
| 新增 | `maze_replay(gameId, detail: "timeline")` | 输出逐回合帧流 + 决策点标注；`summary` / `full` 保留 |

`maze_frames` 的主要消费者是真实逐帧回放与复盘指标系统；在线 Agent 仍只在决策点拿帧，两次决策点之间不允许提交新 `decision`。`fresh observe` 先限定为「上下文恢复 / 调试」，不作为常规战术入口，避免分层退化为每回合决策。

## 9. 必须补的四个硬约束

1. **拼接 ≠ 同源**：见 §6 硬约束 1、2。这是唯一能根治信息错位的写法。
2. **回包分三层**：见 §7。一次性倾倒原始帧会稀释注意力，反而降低决策质量。
3. **帧段要有决策锚点**：标出「上次决策在哪一帧提交、执行了什么计划、`decisionOutcome` 是什么」。否则玩家看到 7 回合轨迹却不知道在评价哪一段计划。锚点就位后，「官方白跑 / 累计无效步数」双口径可顺带实现。
4. **`abandonIf` 的规则定位要改写**：取消 +2 延迟后，它成为两次稀疏决策之间**唯一**的自动应变手段（引擎每回合检查、触发即插入决策点并切出帧段），价值上升而非下降。规则文本应把它从「可选止损」表述为「稀疏决策的补偿机制」。

## 10. 本方案不解决的遗留问题（另案）

| 问题 | 说明 |
|---|---|
| `exit` 终局性 | 与延迟无关，立即生效不解决。需拆 `exit`（结算）与 `headHome`（向出口移动但不结算），否则第 15 局式早退会换个形式重演 |
| 契约与 schema 不一致 | 规则文本要求 `follow` / `deviation`，`maze_decide` 的可调用 schema 为 `additionalProperties: false` 且不接受；`abandonIf` 中断整条 `then` 队列未写入契约；`why: interval` 周期无文档 |
| 白跑口径 | 帧内 `decisionOutcome` 就位后另做「官方白跑 / 累计无效步数」双口径 |
| 计分与平衡（P1） | 成套 +5 阈值化、宝箱奖励不可观测、体力不构成真约束、地图可无集群，均不在本文范围 |

## 12. 验收断言

1. **同源**：构造「同回合拿走目标 + 刷新」用例 → `frame(n).targets` 与 `events` 一致；决策回包逐字段等于 `frame(n)`。
2. **完整性**：一局 `turn = 1…endTurn` 帧连续无缺。
3. **严格回放**：全量帧喂现有 `replay()`，`stateHash` 逐帧一致、终局一致。
4. **立即生效**：提交后 T_n+1 第一步即按新计划移动；不存在 +2 缓冲。
5. **不退化**：对照局决策点次数仍约 6–9 次/局（上批 10 局约 70 次）。
6. **作废归零**：`void_targetGone` 计数为 0；`safetyOverride` 允许少量但须可解释。
7. **可归因**：任一非 `applied` 帧可读出 `decisionOutcome` 原因参数。
8. **兼容**：`maze_replay(summary/full)`、`maze_observe` 默认行为、`maze_decide` 契约不回归。

## 13. 实现后实测计划

- **建立新基线**：规则已变，旧 10 局（合计 53 分 / 均 5.3 / 3 冠军）**不可直接对比**。用同一套策略档案重跑 10 局 XS / `aware`，记录新基线。
- **观测指标**：作废率、安全覆盖率、白跑步数、决策点次数、成套率、均分与名次分布、`memo` 中推断与轨迹的吻合度。
- **机制归因（可选实验）**：把「延迟开关」与「帧拼接开关」做成两个独立开关跑 2×2 对照，量化各自贡献。这属于实验设计，不影响玩家侧规则呈现。
- **平衡性预期**：立即生效 + 完整上下文会让 `then` 全链路连拿更可靠、凑成套更容易，得分天花板大概率上移。若均分涨幅过大，再评估是否收紧体力或调整成套奖励（属 §10 另案）。

## 14. 实现契约（冻结版 · 2026-11-10 待确认）

> 本节以 2026-11-10 对源码的核对为准，**凡与 §1–§13 冲突处以本节为准**。范围（用户已定）：MCP 与网页所有大模型座位一起改；同批做提交防重、`maze_observe` 无副作用、提示词与工具契约对齐；旧成绩作废；MCP 回包为「中文文本 + 末尾 JSON 块」。不改：计分、体力、地图生成、启发式对手、出口规则、决策触发条件及其冷却 / 预算 / 间隔数值。

### C0 对 §1 现状描述的更正

| 原文 | 核对结果 |
|---|---|
| 「决定在 n+2 生效，期间引擎按旧计划走」 | 引擎在第 n 回合开头生成快照后，**先走完 n、n+1 两回合才把决策点交给 Agent**，暂停在 n+2 开头；Agent 思考期间对局不动，提交后用于 n+2 的行动。陈旧来自「交付前已多走两回合」，不是网络慢。开局首个决策点前也已用启发式走了 2 回合。 |
| 「`events` 新、`targets` 旧」的根因 | `observe()` 本身同源；错位发生在 MCP 回包 `pointText()`：把请求时的旧局面、暂停时的自身状态、`g.feed` 的新事件拼在一起。`g.feed.splice(0)` 还会**消耗**事件，重复 observe 看不到。 |
| `maze_observe` 原样返回旧快照 | 没有挂起决策点时它会**推进对局**；有挂起时也会清空事件。 |
| schema `additionalProperties:false` | 当前源码没有该限制；问题是 schema 未声明 `follow/deviation`，而提示词要求填写。 |
| `abandonIf` 每回合检查 | 有在途请求时不检查；`exit` 计划和被体力闸门改写过的计划不检查；触发后清空整条 `then`。零延迟后「在途请求」不再与行动并存，**实际变为每个行动回合都检查**（见 C5）。 |
| `abandonIf=0` 零步重评 | 不成立：要求有可见、在场、负担得起「去目标再回家」的对手且距离不劣于你。 |
| 全量帧喂现有 `replay()` | `replay()` 的输入是种子 + 配置 + 逐回合行动意图 + 哈希，不吃帧；见 C9。 |
| 浏览器需要帧才能逐帧回放 | 浏览器已有真实逐回合回放（拖动、决策跳转）；帧接口服务于 MCP 查询与决策回包。 |

### C1 回合口径

- 对外统一用**帧号 k**：`frame(0)` = 开局、尚未行动；`frame(k)`（k ≥ 1）= 第 k 回合结算后的局面。
- 换算：非终局时内部 `state.turn = k + 1`（即将执行的回合）；终局帧 k = 记录里的终局回合（终局时 `state.turn` 不再递增，不能用 `state.turn − 1`）。
- 决策点基于 `frame(k)`：`snapshotTurn = k`，`effectiveTurn = k + 1`。新计划驱动第 k+1 回合的**第一步**行动。
- 首个决策点在 `frame(0)`：开局任何人行动前就问，不再先走两回合启发式。
- 实现：规划延迟由 2 改为 0（请求发出的同一内部回合立即阻塞、回复后在本回合 `decide` 生效）。不移动 `applyDue` 与 `begin` 的先后顺序。

### C2 适用范围

| 座位 | 是否改 | 说明 |
|---|---|---|
| WorkBuddy MCP 座位 0 | 改 | 对局本来就停在决策点等 Agent |
| 网页 · 玩家 AI 代打（自带 key 契约模式 / 思路模式） | 改 | |
| 网页 · 大模型对手（本地代理 / mock） | 改 | 信息对称。代价：每次有大模型座位决策，**整局暂停等回复**；同一回合多个座位并行请求，等最慢的那个 |
| `llm-eval` 评测、赛后对比里的 mock 对手 | 随默认配置一起改 | |
| 手动、脚本、启发式座位 | 不改 | 不经过规划器 |

网页等待体验：提示条改为「等待 X 决策…」（含玩家自己的 AI，不再显示「等你的脚本返回」）；等待计时照常。暂停期间网络请求继续，回复到达后恢复时立即生效。

接管 / 交还（用户裁定「接管即作废，交还重问」）：玩家接管或换启发式代打时，AI 在途的请求立即撤销（网络请求中止、晚到的回复忽略、不计入本局用量），执行中的计划记 `interrupted`；交还时先补齐接管期间的帧，下一回合开头按当时局面重新问一次（触发原因 `resume`「接管后交还」，不占事件预算）。新开一局 / 关闭对局时，所有大模型座位（含接管期间不在场上的玩家 AI）都撤销在途请求。

### C3 版本与旧成绩

- 新规则版本 `SPEC-0.3`，默认配置 `ai.planLatencyTurns = 0`（字段保留）。配置哈希随之全部更新。
- 旧成绩作废：`SPEC-0.2` 记录不再被服务器认可为当前规则（再次校验为 `unverifiable`）；**数据库数据不删除**。
- 战绩列表照常列出旧局，校验列显示「旧规则 SPEC-0.2」，不给回放按钮（旧配置已不再认可，回放会失败）；MCP `maze_history` 同样标「旧规则（已作废，不可复盘）」。核对后服务器与界面都没有胜率 / 排行等跨局汇总，所以「只计新规则」即体现在这两处。
- `SPEC-0.1` 冻结配置与代码保持现状，不主动删除。
- 记录格式升为 v3（见 C9）；服务器继续接受 v2 / v3 的读取与回放。

### C4 标识与防重

- **决策点 id**：`dp` = 每局每座位从 1 递增的序号，对外形如 `dp-7`。repair（上次提交不合格后的重交）沿用同一 `dp`，另有修复版本 `rev`（0、1）。
- **提交 id**：`submissionId`，客户端自选的字符串（≤ 64 字符），可省略。
- `maze_decide` 外层新增可选参数 `decisionPointId`、`submissionId`；`decision` 内部结构不变。处理规则：

| 情况 | 结果 |
|---|---|
| `decisionPointId` 等于当前挂起点 | 正常处理 |
| 同一 `submissionId` 重复到达（含已处理过的） | 返回第一次的回包，**不再推进** |
| `decisionPointId` 已过期，且没有匹配的 `submissionId` | 拒绝：「决策点 dp-x 已处理」，附当前决策点，**不推进** |
| 不传 `decisionPointId` | 兼容：按当前挂起点处理；回包提示建议带上 |
| 当前没有挂起决策点 | 不应用这次决定；推进到下一个决策点并返回它（正常流程下不会出现，避免对局卡住） |

- **多局歧义**：用户有多局进行中且未传 `gameId` → 返回错误要求指定，不再按「最近一局」猜测。只有一局时可省略。
- 每局保留最近 32 个提交回包用于重试返回；对局结束后随对局释放。

### C5 结果模型（事件流）

不再用单一状态枚举，改为 append-only 的结果事件；每条带 `dp`、帧号 `k`、`targetRef`。

| 事件 | 含义 | 原因参数 |
|---|---|---|
| `applied` | 计划开始执行 | `effectiveTurn` |
| `invalid` | 提交不合法（目标不存在、格式或契约不合格） | 错误说明；首次给 repair 机会（规则不变） |
| `failed` | 调用失败（超时 / 网络 / 熔断，repair 后仍失败） | 失败原因 |
| `cancelled` | 请求还没回就被撤销（玩家接管 / 换控制器 / 对局关闭） | `cause` |
| `interrupted` | 计划执行中被打断（玩家接管 / 换控制器） | `cause` |
| `stale` | 生效时目标已没了 | 新协议下**应恒为 0**，保留用于断言 |
| `guard` | 体力安全覆盖：改为回家 | `dist`、`back`、`stamina` |
| `abandoned` | `abandonIf` 触发 | 对手座位、领先步数 |
| `lost` | 目标被别人拿走 | 拿走者座位、回合 |
| `reached` | 拿到目标 / 开箱 / 到达出口 | 收获 |
| `queued` | `then` 接续下一个目标 | 新 `targetRef` |
| `replaced` | 被下一次决策替换 | 新 `dp` |

- 一个决策可以先后产生多条（例：`applied` → `guard` → `reached`）。历史帧不可变，后发生的结果新增事件，不回写过去。
- 「作废归零」只指 `stale`；`invalid`、`lost`、`guard` 属正常情况，必须可解释（带原因参数）。
- `abandonIf` 的规则文本改写为「稀疏决策之间的自动止损：每个行动回合检查，触发即重新问你，并清空 `then`」，与零延迟后的实际行为一致。

### C6 目标身份 `targetRef`

- 宝石：`{type:'gem', gen, x, y, c}`（`gen` = 宝石代数）；宝箱：`{type:'chest', spawn, x, y}`（`spawn` = 本局第几只宝箱，从开局与刷新事件推导）；出口：`{type:'exit', x, y}`。
- 只在派生层计算，**不进核心状态、不改状态哈希**。
- `decision` 仍提交 `targetType + target{x,y}`；生效时绑定该坐标上的当前实例。同坐标刷出的新一代目标是另一个实例。

### C7 帧与三层回包

**帧来源（同源）**：每回合结算后，用同一份新状态调用 `observe(该座位)` 与公开事件投影生成帧。只含该座位按规则可见的信息；对手的计划、`then`、`abandonIf`、随机数状态一律不出现。

| 层 | 内容 | 何时给 |
|---|---|---|
| 轨迹层 | 每帧：`k`、各座位 `{x,y,stamina,score,status}`、本回合公开事件、本座位当前 `dp` 与 `targetRef` | 决策回包：上次决策点之后到本次的全部帧 |
| 摘要层 | 本段事件按类型分组计数；上一个 `dp` 的全部结果事件 | 决策回包 |
| 决策层 | `frame(k)` 的完整事实表：自身、对手、目标、`race` / `lead` / `rivalsNearer`、地形（沿用现有 payload 结构） | 只在决策点给一次 |

- 同源断言：决策层与 `frame(k)` 来自同一次 `observe` 调用；不再拼接旧快照与新事件。
- 体积：轨迹层单帧约 0.3 KB（XS）；单包最多 40 帧，超出部分只给摘要并提示用 `maze_frames` 取全量。地形不在帧中重复。
- 终局回包包含最后一次决策之后的尾段帧与最终结果事件。
- 网页所有大模型座位的提示词使用同一个构造函数生成轨迹与摘要（与 MCP 同源）；mock 忽略。
- 实现说明（2026-11-10，第 7 项）：planner 收帧时缓存「上一个决策点之后」的帧，发请求时用 `buildPacket` 构造帧段与上次决策的结果（修复重交沿用同一段），存在请求的 `packet` / `trajectory` 上；网页提示词把 `trajectoryText`（摘要正文 + 逐回合位置 JSON）放在 user 消息的局面前面，**对手与玩家自己的 AI 都带完整轨迹**（用户裁定，信息对称）；MCP 取同一个 `packet` 放进末尾 JSON 块（`messagesFor(req, cfg, {trajectory:false})` 避免重复）。实测每次请求平均增加：XS 约 630 字符、M 约 1000、XL 约 1200（约 +15–30%），单次最多约 6000（两次决策隔了 40 回合以上、到帧数上限时）。

### C8 MCP 接口

| 工具 | 约定 |
|---|---|
| `maze_new_game` | 入参不变；返回改写后的规则说明 + 首个决策点（`frame(0)`） |
| `maze_decide` | `decision` 不变；schema 补上可选的 `follow` / `deviation`（与提示词一致）；外层加 `decisionPointId?`、`submissionId?`（C4）；返回下一决策点或终局 |
| `maze_observe` | **纯读**：不推进、不消费事件；返回当前决策点的完整回包，可重复调用结果相同。`fresh:true` 可接受，结果与默认相同（暂停点即最新帧） |
| `maze_frames` | 新增 `(gameId, from, to, fields?)`：只读；进行中对局只给本座位投影且 `to` ≤ 当前帧；已结束对局从记录重演；单次 ≤ 200 帧；`fields` 只能在授权字段内裁剪；仅本人可读 |
| `maze_replay` | `detail` 增加 `timeline`（逐帧 + 决策点与结果事件标注）；`summary` / `full` 保留 |
| `maze_history` | 不变 |

**回包格式**：保留中文正文（时间口径改为「局面是第 k 回合结束后的；你的决定从第 k+1 回合起执行」），末尾附一个 JSON 代码块：

```json
{
  "protocol": "decision-v2",
  "gameId": "…", "decisionPointId": "dp-7", "rev": 0, "why": "complete",
  "snapshotTurn": 23, "effectiveTurn": 24,
  "frames": { "from": 17, "to": 23, "items": [ … ], "truncated": false },
  "summary": { "events": { "pickup": 3, "respawn": 1 } },
  "lastDecisionOutcome": [ { "dp": "dp-6", "type": "applied", "k": 16 }, { "dp": "dp-6", "type": "reached", "k": 21 } ]
}
```

决策层事实表仍在正文里（沿用现有格式），JSON 块不重复。

实现说明（2026-11-10，第 5 项）：
- 正文 = 标题（口径）+ 触发原因 + 摘要层（上次决策的结果事件、本段全场事件按回合）+ 决策层（沿用的局面 JSON）+ 提交指引；逐帧位置只放 JSON 块的 `frames.items`（`seats[i] = [x, y, 体力, 分数, 状态]`，`aim` = 那一回合在执行的 `[dp, 目标类型, x, y]`），正文不重复，控制体积。实测 XS 平均 5.7 KB / 最大 8.1 KB，M 平均 6.2 KB。
- 首个决策点帧段为 `[0, 0]`；之后每个决策点 `(上一个决策点的帧号, 本次帧号]`；终局回包带 `(最后决策点帧号, 终局]` 尾段与最后一次决策的全部结果事件。
- 回包在到达决策点时生成一次并缓存：`maze_observe` 与带同一 `submissionId` 的重试都原样返回它。
- `maze_frames` 目前读进行中（及刚结束、仍在内存里）的对局；已入库的对局从录像重建帧在第 6 项实现。

### C9 记录与回放

- 记录 v3：`plan` 行增加 `dp`、`rev`；新增 `outcome` 行记录 C5 的结果事件。行动意图与状态哈希不变，严格回放逻辑不变。

实现说明（2026-11-10，第 6 项）：
- `outcome` 行记**所有大模型座位**（用户裁定），在每回合结算前（applied / invalid / queued / guard / abandoned / replaced / 撤销）与采帧后（reached / lost）写入，都在 `end` 行之前；玩家接管时被换下的控制器的 `cancelled` / `interrupted` 立即写入。
- 大模型规划器所在座位**总是采帧**（reached / lost 靠帧判定），调度器的 `frames` 选项只能额外加座位。
- 帧重建 `src/record/frame-replay.js`：严格回放 + 逐回合 `observe` 投影；v3 的结果事件取自 `outcome` 行（`anchors: "recorded"`），v1 / v2 只给帧（`anchors: "derived"`，`aim` 为空）。
- 服务器校验器：`outcome` 行只做形状检查（座位、dp、帧号、类型白名单），是自报的复盘信息，不影响 verified；v1 / v2 记录出现 `outcome` 行直接拒绝；行数上限放宽到 `maxTurns × 12 + 8`。
- 实测体积：XL 整局四个大模型座位 65–72 KB（gzip 约 9 KB，其中 outcome 行约 27 KB），远低于 1 MiB。
- MCP：`maze_frames` 对进行中 / 刚结束仍在内存里的对局读实时帧，闲置清理后从入库录像重建（结果与实时帧逐字段一致）；`maze_replay` 新增 `detail: "timeline"`（逐帧 + 决策点列表 + 结果事件，分页同 `maze_frames`）。旧规则（SPEC-0.2）的对局配置已不认可，复盘时明确提示。
- 帧不入记录：已结束对局的帧由「记录严格回放 + 逐回合 `observe` 投影」按需重建。
- 校验分两层：记录严格回放（哈希逐回合一致）；帧重建一致性（重建出的帧与对局中实际下发的逐字段一致）。
- v2 旧记录可回放；它没有 `dp` / `outcome`，`timeline` 中的决策锚点标为「推导」，不伪造。
- 记录体积上限 1 MiB 不变；需验证 XL 局加上 `outcome` 行后不超限。

### C12 验收（替代 §12）

1. **同源**：决策层与 `frame(k)` 来自同一次投影；构造「同回合拿走 + 刷新」用例，目标表与事件一致；同坐标新一代目标被识别为新实例。
2. **零缓冲**：提交后第 k+1 回合第一步就按新计划移动；首个决策点在 `frame(0)`；MCP 与网页各有用例。
3. **`stale` 归零**：固定种子对照局中 `stale = 0`；`invalid` / `lost` / `guard` 均带原因参数。
4. **连续性**：一局 `frame(0…终局)` 连续无缺；决策回包的帧段首尾与上次 / 本次 `dp` 衔接，终局含尾段。
5. **防重**：同一 `submissionId` 重试不推进、返回同一回包；过期 `dp` 被拒且不推进；多局未传 `gameId` 报错。
6. **纯读**：`maze_observe` 连续调用两次结果逐字节相同，对局回合不变；`maze_frames` 不推进。
7. **不越权**：帧中不出现对手计划 / `then` / 随机数；他人对局的帧读不到。

**等待动作**（所有大模型座位，配置 `ai.wait = {maxTurns 10, maxTotal 40, stopAtMax 3, timeMargin 2}`）：
- `{"targetType":"wait","turns":k}`：原地等 k 回合（1–10，默认 3）。`{"targetType":"home","stopAt":s}`：沿回家最短路走到离出口 s 步（1–3，默认 1）的格停下等，最多 10 回合，绝不踩进出口。生效时定下等待格（结果事件 `ref {type:'wait'|'home', x, y}`）。
- 在等待格上每回合原地不动、不耗体力。等满 → `woken {cause:'expired'}`（计划行 `src:'wake'`，不算决策），`then` 有下一个就接着走，否则必问；本局累计满 40 → `woken {cause:'cap'}`，再交等待判不合格重交。
- 等待中：刷新叫醒必问（`woken {cause:'refresh'}`，回 keep 接着等，计数累计）；对手接近 / 受阻 / 体力终盘 / 定期都不问。
- 时间闸门：剩余回合 ≤ 回家步数 + 2 → 结束等待、改回出口（`guard {cause:'time'}`）。
- `then` 可写等待；`abandonIf` 对等待不起作用；旧规则配置（无 `ai.wait`）交等待判不合格。
- 录像只记原地不动，严格回放与校验不变；复盘「原地等了 n 回合，到期 / 被刷新叫醒 / 改了主意」。
