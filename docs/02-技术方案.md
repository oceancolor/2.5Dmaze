> **#20 阈值为什么必须是纯比例 `×1.3`（不接受 `×1.15 + 8` 这类带常数项的形式）**：常数项在大尺度下失效。`+8` 在 `d=10` 时给 80% 余量（等于天天误报），在 `d=200` 时只剩 4% 余量（等到告警时已经走不回去了），**同一个公式在不同距离尺度上的语义完全不一致**。纯比例 `×1.3` 是尺度无关的：`d` 取任何值，告警都在"还剩 30% 冗余"那一刻触发。QA 的 E-S2 三档尺度无关断言（含 `d=200 / stamina=250`）守的就是这条。同一公式在 §8 降级链 L1 的 `HeuristicPolicy` 里复用，**两处必须同值**——罗盘给玩家看的告警和 AI 自己决定回家的判据如果不一致，玩家会看到"绿灯但 AI 掉头"的荒谬画面。

## 1. 技术选型：渲染栈（引擎中立评估）

用户已定「网页版」，故候选池为 Web 侧渲染/游戏方案。评分是我的判断，权重按 **A1/A2 前提**（桌面 + 单人小团队）设定，换前提请勿直接套用结论。

### 1.1 候选评分表（10 分制）

| 维度 | 权重 | Canvas2D 原生 | WebGL 原生 | PixiJS 8 | Phaser 3 | Three.js | Godot Web 导出 |
|---|---|---|---|---|---|---|---|
| 45° 等距砖块渲染契合度 | 0.20 | 9 | 9 | 9 | 10 | 4 | 8 |
| 上手成本（单人小团队） | 0.20 | 10 | 4 | 7 | 8 | 5 | 6 |
| 依赖体积 / 立项速度 | 0.15 | 10 | 9 | 6 | 4 | 3 | 2 |
| 128×128 性能余量 | 0.15 | 8 | 10 | 9 | 8 | 10 | 8 |
| UI/输入/音频现成度 | 0.10 | 3 | 2 | 6 | 9 | 4 | 9 |
| Web Worker 沙箱集成难度 | 0.10 | 9 | 8 | 7 | 6 | 6 | 3 |
| 长期维护/迁移成本 | 0.10 | 8 | 6 | 7 | 7 | 6 | 5 |
| **加权总分** | 1.00 | **9.50** | 7.05 | 7.45 | 7.60 | 5.35 | 5.00 |

### 1.2 结论

**选 Canvas 2D 原生（零第三方运行时依赖）。**

理由三条：

1. 本作本质是「AI 驱动的回合制棋盘游戏」，渲染是次要矛盾。游戏引擎带来的编辑器、场景树、物理、动画状态机，在本作里的收益接近 0。
2. 分块预烘焙后，**每帧静态层只有 ~40 次 blit**（§2.3 有推导），Canvas2D 的性能余量足够，不需要为此引入 WebGL 的批处理/着色器维护成本。
3. Web Worker 沙箱（玩家脚本）必须与渲染完全解耦才有安全感，引擎越少越好管。

**第二名 PixiJS**（若 P2 要做大量粒子/光影，可只替换 `src/render/` 目录）。
**反悔成本**：`render/` 目录是本方案的唯一渲染边界，`core/` 不引用任何绘制 API。换渲染栈的成本 ≈ 重写 `src/render/` 5 个文件，不影响玩法与 AI。

## 2. 渲染方案

### 2.1 坐标与几何参数（建议值）

| 参数 | 取值 | 说明 |
|---|---|---|
| 投影 | 2:1 菱形等距（dimetric） | 视觉上的"45 度仿 3D 俯视角" |
| 地块宽/高 `tile.w × tile.h` | `64 × 32` | 标准 2:1，美术好切图 |
| 屏幕变换 | `sx = (gx-gy)*32 + camX`；`sy = (gx+gy)*16 + camY` | 全部走 `render/iso.js`，别处不许手算 |
| 全图屏幕包围盒 | `8192 × 4096 px` | = 128×64 宽、128×32 高 |
| 1080p 视口可见地块 | **2025 格** | `1920*1080 / (64*32/2)` = 2025（几何精确值） |

### 2.2 三层结构

| 层 | 内容 | 重绘触发 | 每帧成本 |
|---|---|---|---|
| **静态层** | 地面、墙体棱柱、地面装饰 | **永不**（地图生成后不变） | ~40 blit（见 §2.3） |
| **动态层** | 4 角色、5 宝石、1 宝箱、移动指示、拾取飘字 | 每帧 | ≤ 48 drawImage |
| **HUD** | 体力/分数/回合数/回放控制条 | 状态变化时 | **用 DOM/CSS，不占 canvas 预算** |

> 关键收益：**因为否决了战争迷雾，三种视野模型都不做"未探索涂黑"，静态层永远不需要失效重烘焙**，省掉了脏矩形追踪整套机制。这是"迷雾不要"在工程上的额外红利。

### 2.3 分块（chunk）缓存

| 项 | 取值 | 推导 |
|---|---|---|
| 分块粒度 | **8×8 地块** | 太小 blit 多、太大内存抖；8×8 是 2025 格时代的甜点 |
| 分块位图尺寸 | `512 × 256 px` | `宽 = n*tileW = 512`，`高 = n*tileH = 256` |
| 单块内存 | **0.5 MB**（RGBA） | `512*256*4 = 524,288 B` |
| 全图块数 | 256 块（16×16） | 全缓存 = 134 MB → **不可全缓存** |
| LRU 上限 | **64 块 = 32 MB** | 见 §3 内存预算 |
| 每帧 blit 数 | **≤ 48（1080p）/ ≤ 80（1440p）** | 覆盖 2,073,600 px 需 31.6 块有效面积 + 边缘 ~10 块；1440p 同理 ~66 |
| 缺块重建成本 | 64 次 drawImage（≤ 0.6 ms） | 只在摄像机大幅跳转的第 1 帧发生 |

### 2.4 摄像机 / 全图 / 小地图

| 能力 | 做法 | 成本 |
|---|---|---|
| 摄像机跟随 | 跟随玩家角色，边缘阻尼，`zoom` 两档离散：1.0 / 0.6 | 缩小时 blit 同一批分块（GPU 缩放） |
| **全图浏览** | **不做第三个渲染管线**——缩到 0.6 已经是全图语义（8192*0.6=4915 px，配合拖拽） | 0 |
| **小地图** | 独立 canvas `256×256`，**正交俯视**（非等距），地图部分只画一次，实体用脏点更新（每回合 ≤ 8 个 4×4 px 点） | 每回合 < 0.2 ms |
| 128×128 全图缩略不卡的要点 | **绝不实时遍历 16384 格**：地图层一次性栅格化后缓存；只有实体走脏矩形 | — |

## 3. 性能预算

> **准入说明**：本表每项都绑定了「自动降级」或「门禁卡点」。
> **自动降级**列的函数名与阈值是**契约定义**——P1.5 实现时必须落地为同名同签名的函数、使用表内数值；QA 阶段以「降级路径可被调用且真实降低 drawcall」断言。若届时未实现，该行降级为门禁卡点，不得留空。

| # | 指标 | 目标 | 测量方式 | 超阈处置 |
|---|---|---|---|---|
| P1 | 稳定帧率 | ≥ 58 FPS 均值；1% low ≥ 45 FPS | `RenderStats` 环形缓冲 300 帧，dev-overlay 实时显示 | **自动降级**：连续 60 帧帧时间 > 16.7 ms → `Quality.stepDown()`：L2→L1 关墙体投影/描边（重烘焙静态块）；L1→L0 关 idle 动画帧率减半 + zoom 强制 0.6 |
| P2 | 单帧 canvas 绘制操作数 | ≤ 80 @1080p（含分块 blit + 动态层） | `Renderer.stats.drawOps`，每次 drawImage +1 | **自动降级**：>80 连续 30 帧 → `Quality.stepDown()`；>120 立即再降一级并写 `console.warn` |
| P3 | 单帧 JS 逻辑耗时（不含绘制） | ≤ 4 ms（回合逻辑 + 插值动画） | `performance.now()` 打点差值 | **自动降级**：>6 ms 连续 20 帧 → 关闭移动插值（`motion.interpolate=false`），改为瞬时落位 |
| P4 | 地图就绪总耗时（生成 + 4 次全图 BFS + 挖空地 + 预生成 4 组宝物点） | P95 ≤ 20 ms（**实测 P50 2.70 / P95 3.94 ms**，单帧峰值 38.7 ms 出现在 JIT 预热期） | `tools/bench-maze.mjs` 跑 1000 种子输出分位数 | **门禁卡点**：P95 > 20 ms 阻断合入；判定人：架构。**前置要求**：候选池每图只建一次、离散度计算内联零分配、远点采样增量维护最小距离——朴素写法实测 P95 会到 53.9 ms，直接超标 |
| P5 | 单次全图 BFS | ≤ 1.5 ms（实测 0.24 ms） | 同上 | **门禁卡点**：>1.5 ms 阻断合入；处置：换 Int32Array 队列 + 复用缓冲池 |
| P6 | JS 堆内存 | ≤ 200 MB | Chrome Memory Snapshot（10 分钟自动对局后） | **门禁卡点**（浏览器无强制 GC，无法运行时回收）：超标阻断合入 |
| P7 | Canvas 位图内存 | **≤ 48 MB**（明细见表后） | 分项统计：`ChunkCache.stats().bytes` + `TintCache.bytes` + 图集解压（512²+1024² 恒 5 MB）+ 小地图/离屏 | **自动降级**：分块达 64 块立即 LRU 淘汰；若仍超 48 MB → `ChunkCache.setMax(32)`（省 16 MB） |
| P8 | 页面总内存 | ≤ 350 MB | Chrome 任务管理器（Shift+Esc） | **门禁卡点**：超标阻断合入 |
| P9 | 冷启动首帧 | ≤ 1.5 s（本地 http） | `PerformanceObserver` + 自定义 `firstInteractive` 打点（仅本地显示） | **门禁卡点**：>1.5 s 阻断合入 |
| P10 | 输入 → 画面反馈 | ≤ 80 ms | `performance.now()` 输入事件到首帧移动差值 | **门禁卡点**：>80 ms 阻断合入 |
| P11 | 静态资源总量 | ≤ 4 MB（JS ≤ 300 KB，图集 ≤ 2.5 MB，字体 ≤ 200 KB） | `tools/size-budget.mjs` 遍历 `dist/` | **门禁卡点**：脚本退出码非 0，阻断提交（pre-commit / CI 挂该脚本） |
| P12 | 首屏必需资源 | ≤ 1.2 MB | 同上 | **门禁卡点**：同上 |

**P7 内存明细（并入美术的 tint 缓存与图集解压后重算）**

| 项 | 内存 | 备注 |
|---|---|---|
| 分块 LRU（64 × 512×256 RGBA） | 32.0 MB | 硬上限，可降到 32 块 |
| 图集解压（512² + 1024²） | 5.0 MB | 常量，与地图无关 |
| AI 三只 tint 缓存（3×40 帧×64²） | 1.97 MB | boot 一次烘焙，运行期只读 |
| 小地图 + 杂项离屏 | ~2.5 MB | |
| **合计** | **≈ 41.5 MB** | 预算 48 MB，余量 6.5 MB |

> **为什么这几项只能归"门禁"**：P6/P8/P9~P12 **没有运行时降级空间**——内存不能凭空变小、已加载的资源不会消失、已发生的冷启动耗时无法回退。给它们硬造一个运行时降级动作才是过度工程。判定人均为架构，判定环节均为"合入前"。

## 4. 工程架构

### 4.1 分层

```
┌──────────────────────────────────────────────────────────┐
│  ui/          HUD · 设置面板 · 回放面板（DOM/CSS）        │
├──────────────────────────────────────────────────────────┤
│  render/      等距变换 · 分块缓存 · 图集 · 摄像机 · 小地图 │  ← 唯一渲染边界
├──────────────────────────────────────────────────────────┤
│  player/      输入 · 脚本宿主 · Worker 沙箱               │
│  ai/          LLM 客户端 · 观察编码 · 重规划节流 · 启发式 │
│  net/         本地代理客户端（只允许 127.0.0.1:8787）      │
├──────────────────────────────────────────────────────────┤
│  core/        状态 · 调度器 · 规则 · 迷宫 · 寻路 · rng     │  ← 纯逻辑，禁止触碰 DOM/网络/计时器
│  record/      JSONL 记录 · 回放 · stateHash               │
├──────────────────────────────────────────────────────────┤
│  config/      default.config.js（所有可调数值的唯一出处）  │
└──────────────────────────────────────────────────────────┘
```

**依赖方向严格单向向下**。`core/` 不得 `import` 任何上层模块；上层通过注入获得 core 的对象。

## 6. 迷宫生成与可达性

### 6.1 算法（实测数据支撑）

**选定：Growing Tree（混合选择率）+ 编织去死胡同 + 挖房间 + 削墙控密度。**

为什么不选别的：

| 候选 | 128×128 实测/判断 | 结论 |
|---|---|---|
| Recursive Backtracker（纯 DFS） | O(N) 快，但走廊极长死胡同多，宝物藏进去没人愿意绕 | 作为 Growing Tree 的一个参数端点（newest=1.0）保留 |
| Prim / Kruskal | 同量级，更碎分支，缺少长走廊的"赶路感" | 不做 |
| **逐格随机障碍+连通修复** | 不是迷宫，是一坨随机点；没有路径趣味性 | 否 |
| **stride-1 Growing Tree** | 实测：几乎不产生墙（密度 0.031，15876/16384 是地板），退化成空地 | 否（重要陷阱：128×128 逐格生长会退化） |

**旧做法把宝物全挤死在地图中心** —— 实测比我先前向创意总监汇报的还要严重：

| 目标函数 | 逐颗离散度 | **五颗总距离离散度** | 宝石到地图中心平均距离 | 两两最小间距 | 五颗包围盒边长 |

**由此得到两条必须改的东西**：

1. **逐颗 0.35 的门槛必须放宽到 0.90**。只放宽到 0.35 也只能把宝石推到距中心 16 格，仍然挤。放宽到 0.90 后包围盒 123.7 格 ≈ 铺满整张地图。
2. **真正的公平约束交给"全体总距离"（`aggregateMax = 0.35`）**。实测：即使逐颗离散度放到 0.73，五颗总距离的离散度均值只有 **0.124、P90 0.240，100 张图里 0 次破 0.35**。原因是分散天然让每颗偏向不同角落，四人的**总和**自动扯平。**这恰好实现了"整体公平、局部有领地感"。**

> **还有一条边界是创意总监没预见、仿真跑出来才发现的**：把"最大化分散"放到极致（10 颗时不设半径限制），宝石会被甩到距中心平均 **90.6 格**的四角，成为没人够得着的**死宝石**。因此必须加一条 **`maxRadiusFromCenter = 55`** 的上界：

| 10 颗时的半径约束 | 到达率 | 人均分 | 人均宝石 | 一个都拿不到占比 | 平均回合 |
|---|---|---|---|---|---|
| 不限制 | 90% | 2.83 | 2.09 | 13% | 411 |
| **距中心 ≤ 55（推荐）** | **91%** | **3.11** | **2.40** | **10%** | 410 |

下界不必限制；**上界 ≤55 是唯一必要的那条**，它把"限fill屋顶作用力和 dead tiles"都消掉了。

其他：撒点前先算好四出生点的距离场（实测 **1.15 ms/图**），候选池逐个 ℓ online 判定，硬校验 `aggregateMax=0.35` 不满足时最多重试 20 次取最优。宝石**开局一次性预生成 3 组**（`pregenerateSets=3` = `gemGenerations`）用于重生，零中途开销且完全确定性。

#### 6.7.2 五条结论

1. **体力 400 锁定** ✅（在 v1.5 全规则下重跑，与 v1.4 结论一致）。
2. **宝箱 `[25,50]` 不雪球** ✅：实测每局开箱 **2.00~2.13 次**（上限 3），成功者剩余体力 74~90。我原先担心的"3 次 × 50 = +150 体力"没有发生——60 回合重生间隔 + 往返成本让第三次开箱常常来不及。**可放行**（⚠ 仍待用户确认，因偏离原需求 [5,10]）。
3. **僵持兜底是承重墙，不是死代码** ⚠：实测每局触发 **67~85 次**（占 actor-回合数 ~4.5%）。四人抢同几颗宝石时互相阻挡极频繁，**没有这条兜底会陷入永久 −0 僵持**。
4. **四面全阻兜底几乎不触发**（0.9~3.1 次/局），但**不能删**：它是唯一覆盖"被其他角色从四面包围"这种非地形死锁的分支，触发率低是因为罕见，不是因为冗余。
5. **单局时长：平均 383 / P90 419 / 最大 453 回合，>480 回合占比 0%** ✅ —— `maxTurns=600` 兜底实测永不触发，且这是 X13=360 额度的算账依据（见 §8.4.1）。

#### 6.7.3 关于「主动停留扣 1」的诚实结论

本轮仿真里这条规则**一次都没生效**——启发式策略从不主动原地不动（要么走向目标，要么走向出口）。所以：

- ✅ 它对 400 这个甜点位**没有影响**，不需要改数值；
- ✅ 但**值得保留**：它关掉"永远站着不动、只能靠 `maxTurns` 兜底"的漏洞。任何 actor（尤其是**玩家手写脚本**或跑偏的 LLM）只要选择停留就必须付费，回合数因此天然收敛。**这条规则的实际服务对象是玩家脚本，不是 AI**——AI 用不上恰好说明 AI 侧行为正常；
- ⚠️ 副作用：被阻挡扣 0，被卡住的回合是"免费"的，这是把对局拉到 382 回合的主因。仍远低于 `maxTurns=600`。若日后要压时长，旋钮是 `maxTurns`，**不是体力**。

### 7.2 冲突仲裁与体力扣减（D4 / D5b 已裁定，已用于仿真）

**体力扣减规则（v1.5 终稿）**

| 情形 | 扣减 | 备注 |
|---|---|---|
| 正常移动一格 | **-1** | |
| **主动停留**（actor 自己选择不动） | **-1** | 关闭"永久原地拖延"漏洞 |
| **非法意图**（撞墙 / 越界 / 被禁的互换） | **-1** | 与主动停留同价 |

### 7.3 确定性（QA 的硬前提）

| 风险源 | 强制手段 | 验证门禁 |
|---|---|---|
| `Math.random` 混入逻辑 | 只允许出现在 `core/rng.js` | **`tools/lint-determinism.mjs`** 扫描 `src/core/**` 与 `src/ai/**`，命中退出码 1（挂 pre-commit + CI） |
| `Date.now` / `performance.now` | 只允许出现在 `core/clock.js`，其余一律注入 `Clock` | 同上，同一个脚本一并扫 |
| Map/Set 迭代顺序 | 需要稳定顺序处显式 `sort()` by id | `determinism.test.mjs` |
| 浮点累积误差 | 分数/体力**只用整数运算**；若出现除法（如 ratios）一律 `Math.floor` 到整数，禁止浮点入 state | `scoring` 单测 |
| **异步决策到达顺序** | `DECIDE` 只收集，`SORT` 排序后才裁决 | `determinism.test.mjs`：打乱 3 个 Promise 的 resolve 顺序，断言最终 `stateHash` 完全一致 |
| LLM 输出 | `temperature=0` + **原文完整记录** | 回放断言逐回合 hash 相等 |
| 玩家脚本 | 每次返回的决策与耗时全部记录 | 回放以记录为准 |
| 随机流互相污染 | **具名流**：`rng.stream("maze"｜"treasure"｜"chest")`，各流独立推进 | 加一个子系统不再打乱其他流 |

**核心门禁（不可妥协）**：
```
同 seed + 同回放记录 ⇒ step() N 次后的 stateHash 必须逐回合完全相等
```
`stateHash` = 对 canonical JSON（`JSON.stringify` 键序由构造保证）做 FNV-1a 32-bit。

### 7.4 对局记录格式（JSONL，每行一条）

| type | 载荷 | 用途 |
|---|---|---|
| `meta` | `{v, seed, configHash, rulesVersion, createdAt}` | 回放前校验；`configHash` 不匹配则拒绝严格回放 |
| `turn` | `{n, actors:[{id, decision:{dir｜target}, source:"llm｜cache｜heuristic｜script｜input", latencyMs, rawPlan}]}` | 回放的决策来源 |
| `event` | `{n, type:"gem.pickup｜chest.open｜blocked｜exit.reached", ...}` | 断言用 |
| `hash` | `{n, h}` | 逐回合哈希比对 |

回放模式：`strict`（完全按记录，断言 hash 相等）。`resume`（第 N 回合起改由 AI 接管）**延后到 P2**，本轮不做。

### 8.2 Key 安全（本地代理形态）

| 项 | 做法 |

### 8.3 三个 AI agent 的调用编排

| 问题 | 结论 |
|---|---|
| 并发还是串行 | **并发**（`Promise.allSettled`，并发上限 3）。串行会让单回合等待时间×3 |
| 三个 agent 看到的信息 | **必须是同一份 `TURN_START` 快照**，否则先决策者占信息便宜 |
| 每次调用给什么 | 观察快照（≤ 15×15 视野窗口，ASCII ≈ 70 token）+ 自身状态 + 可见/记忆的动态实体 + 候选目标。**绝不给全图** |
| 输出格式 | `{targetType:"gem｜chest｜exit", target:{x,y}, reason:"…"}`，≤ 200 output token |
| 落地执行 | **LLM 只出高层目标点，本地 `nav/bfs` 距离场执行单步移动** —— 这是节流的核心 |
| 距离场复用 | 目标点不变时，距离场跨回合缓存（每个 agent 上限 4 张场 × 32 KB = 128 KB，全图 512 KB，可忽略）；每回合走一步只是 O(1) 查表 |

### 8.4 节流方案（这是本项目成本与博弈性的核心取舍）

以 **4 agent / 单局 382 回合（§6.7 实测平均）** 为基准估算：

| 方案 | 调用数/局 | token/局 | 博弈质量 | 延迟敏感度 | 结论 |
|---|---|---|---|---|---|
| A 每回合每 agent 都调 | 1528 | ~1.38 M | 最高 | 极高（每回合 8 s 超时风险） | ❌ 不推荐：成本与延迟都不可接受 |
| **B 每 K=8 回合重规划 + 事件触发（推荐）** | **232**（最坏 268） | **~0.21 M** | 高（策略层主导，执行层本地化） | 低 | ✅ 默认（X13 上限 360） |
| C K=20 + 仅全局目标 | ~84 | ~0.08 M | 中（反应迟钝，容易被抢） | 极低 | 省钱档 / 上游限流严重时降级 |
| D 纯启发式 | 0 | 0 | 低（无惊喜） | 无 | 兜底 & QA 对照基准 |

**取舍要害**：LLM 的价值在**判断"值不值得绕"**（战略），而不是**算"下一步走哪"**（算术）。算术交给本地 BFS，成本降 **~85%**，而博弈性损失很小——因为本作的决策频率是"每 8 步重估一次局势"，这恰好接近人类在该节奏下的思考频率。若未来发现 AI 显得呆板，只需把 `replanInterval` 从 8 调到 4，无需改代码。

**事件触发重规划**（设计案 v1.7 §4.7 终稿 6 条 + 可选第 7 条）：

| # | 事件 | 确切触发条件 | 类型 |
|---|---|---|---|
| 1 | 目标失效 | 当前目标点上的宝石 / 宝箱已消失（含被他人吃掉） | **边沿**（天然） |
| 2 | 宝物刷新 | 新一代宝石重生 或 宝箱重生（全局广播） | **边沿**（天然） |
| 3 | 路径受阻 | 连续 **2** 个回合未发生位移 | ⚠ 现状按**状态**判定 |
| 4 | 体力告警 | `剩余体力 ≤ d(→exit) × 1.3`（**X11 动态阈值**，替换原"跌破 25%"） | ⚠ 现状按**状态**判定 |
| 5 | 高价值出现 | 视野内出现 **≥1 颗**自己尚未持有颜色的宝石（从 ≥2 放宽到 ≥1） | ⚠ 现状按**状态**判定 |
| 6 | 对手进入视野 | 视野内出现任何其他角色 | ⚠ 现状按**状态**判定 |
| 7（可选） | 冲刺窗口 | 已持有 ≥3 色 且 `d(→exit) ≤ 25` | ❌ **实测 100 局零触发，已删除**（人均只拿 2.47 颗，凑不齐 3 色） |

> ⚠ **事件③④⑤⑥ 的判定类型是本轮实测的关键变量**——"状态型"（条件满足即候选，冷却一过再触发）与"边沿型"（只在从不满足→满足的跃迁那一刻触发）的实测差异见 **§8.4.3**：**P90 从 80 降到 10**。**实现前必须先定这一条**，否则事件额度会被"对手还在视野里"这种无新信息的重复触发吃光。

#### 8.4.1 调用额度算账（X13=360，实测回合分布代入）

基准：**4 agent**（不是 3）、**`replanInterval=8`**、**事件每 agent 每局 ≤10 次**（`eventBudgetPerAgent`，见 §8.4.3 实测）。代入 §6.7 实测回合分布（平均 382 / P90 421 / 最大 454）：

| 局面 | 回合 | 每 agent 重规划 `⌈T/8⌉` | + 事件 10 | 每 agent 小计 | 全局 ×4 | **对 360** |
|---|---|---|---|---|---|---|
| 平均 | 382 | 48 | 10 | 58 | **232** | ✅ 余 128 |
| P90 | 421 | 53 | 10 | 63 | **252** | ✅ 余 108 |
| 最大 | 454 | 57 | 10 | 67 | **268** | ✅ **余 92** |
| `maxTurns` 理论上限 | 600 | 75 | 10 | 85 | **340** | ✅ 余 20 |

> ⚠ 上表是**最坏上界**（假定 4 个 agent 全部吃满 10 次事件额度且都跑到同长度）。§8.4.3 实测：事件改边沿触发后每 agent 每局**均值 6.9 / P90 10**，多数局远低于上界，实际期望 ≈ **216 次/局**。

**结论：360 在所有观测到的局面下都不触顶**（最大局余 108，理论上限局余 36）。

> **为什么是 360 而不是 240**（主理人终裁口径，我认同）：240 在 6 次事件上限下**只有最大局超 12 次**，本来也够用。但触顶不是"报错"，是"**有 agent 在终盘前被降级成启发式**"——那是**卖点受损**，不该是常态。360 买的是"最大局也不触顶"。触顶率从 ≈10%（240 口径）降到接近 0。

#### 8.4.2 额度分配与触顶处置（写死，不允许"尽量省"）

| 步骤 | 规则 | 数值 |
|---|---|---|
| ① 先扣终盘预留池 | `endgame.reserve = 8` 次/agent × 4 = **32**，**锁死，常态调用不得占用**。**这是池内划拨，总量不变** | 360 − 32 = **328** |
| ② 常态池先到先得 | 4 agent 共享 328；每 agent 软上限 **82**（`perAgentBudget 90 − 8`） | — |
| ③ 触顶判定与处置 | 某 agent 常态额度用尽 → **该 agent 转 `HeuristicPolicy`**，写入 `source:"heuristic"`；**其他 agent 不受影响** | 触发点：`ai.callsUsed[agentId] >= 82` |
| ④ 终盘池解冻 | 进入最后 60 回合 → 终盘池解冻，每 agent 保证 8 次，间隔**无条件回调 8** | 触发点：`turnsRemaining <= 60` |
| ⑤ 终盘额度也用尽 | 转 `HeuristicPolicy` 并在终局记录标记 `endgameBudgetExhausted: true` | 供 QA 断言 |

**总量恒等式（写成断言）**：`常态调用数 + 终盘调用数 ≤ 360`，**不存在"终盘豁免"**。分池只是为了**保证终盘拿得到**，不是为了增加总量。

**为什么要先扣终盘池**：这是 **360 与 G09b（最后 60 回合每 agent ≥8 次调用）唯一可能打架的地方**。若不分池，前面跑得久的 agent 可能把额度吃光，导致终盘保底发不出 → G09b 断言失败。分池后 G09b 由构造保证（预留 8 次/agent 恒在），与种子无关。

**G09 判据校准**：判据写 `≤360`（非终盘）即可，**不会 fail** —— 前提是**实现按"池内划拨"做**。若实现按"豁免"做，全局观测值会变成 392，G09 稳定 fail。**这就是 §5 那句注释必须在代码里也写一遍的原因。**

**X14 与 X13 的关系**：中盘降本把间隔拉到 `replanIntervalMax=10` 时，382/10=39+6=45×4=**180**，余量充足。降本档位不再是 360 的保险丝，而是**成本优化手段**。终盘无条件回调 8、终盘不参与任何降本，两条不变。

#### 8.4.3 ⚠ 事件次数实测：**问题不在上限值，在事件③④⑤⑥ 的判定类型**

主理人要求实测后裁定「每 agent 每局事件上限 6 次」的存废。100 局 / 4 agent / 取消次数上限 / 只保留冷却，沿用 §6.7 仿真框架（事件清单 = §8.4 的 6 条 + 可选⑦，视野半径 R=9 切比雪夫，④用 X11 动态阈值）：

| 判定类型 | 冷却 | 每 agent 均值 | **P50** | **P90** | P95 | **max** | 全局/局 均值 | 全局 max |
|---|---|---|---|---|---|---|---|---|
| **状态型**（现行定义：条件满足即候选，冷却一过再触发） | ≥3 | 31.2 | 21 | **80** | 95 | **122** | 124.6 | 353 |
| 状态型 | ≥5 | 19.6 | 13 | **49** | 58 | 73 | 78.3 | 211 |
| **边沿型**（建议：只在"不满足→满足"跃迁那一刻触发） | **≥3** | **6.9** | **6** | **10** | 11 | **21** | **27.4** | **44** |
| 边沿型 | ≥5 | 6.2 | 6 | 9 | 9 | 15 | 24.9 | 39 |

| ⑤ | 高价值出现 | 7.25 | 23.2% | ⚠ 状态型：宝石在视野里待着就一直触发 |
| ⑥ | **对手进入视野** | **26.57** | **85.2%** | ⚠ **状态型是错的**：两个角色在视野内互相耗着，冷却一过就再触发一次，**这在语义上是"对手还在视野里"，不是"对手进入视野"** |
| ⑦ | 冲刺窗口 | **0.00** | 0% | ❌ **死事件**：要求"≥3 色 + d≤25"，实测 100 局零触发 |

> 注：分项之和 > 总数，因为一次触发可能同时命中多条（冷却合并为一次调用）。

**三条处置建议**：

1. **③④⑤⑥ 全部改边沿触发**（⑥ 尤其必须改——事件名就叫"**进入**视野"，状态型实现是名实不符）。改后 P90 从 **80 → 10**，降 **87%**。这是本轮性价比最高的一处修改，**且零玩法损失**：边沿触发捕捉的正是"局势发生变化"的瞬间，状态重复触发给 LLM 的是**同一份观察**，不产生新决策。
2. **`eventBudgetPerAgent` 6 → 10**（= 边沿型冷却 ≥3 的 P90 向上取整）。改后算账：

   | 局面 | 基准重规划/agent | + 事件 10 | 全局 ×4 | 对 360 |
   |---|---|---|---|---|
   | 平均 382 | 48 | 58 | **232** | ✅ 余 128 |
   | 最大 454 | 57 | 67 | **268** | ✅ 余 92 |
   | 理论 600 | 75 | 85 | **340** | ✅ 余 20 |

   **全部不触顶。** 上限 10 的作用是挡住"某个 agent 恰好连续遭遇"的长尾（max 21），不是省成本。
3. **事件⑦（冲刺窗口）直接删除**：实测 **100 局零触发**（要求"≥3 色 + `d(→exit) ≤ 25`"；人均只拿到 2.47 颗，凑不齐 3 色的情况下根本进不了这个窗口）。留着是死代码，QA 应判为不可达分支。

**关于降本阶梯④「冷却 ≥3 → ≥5」**：实测只能把全局事件从 27.4 降到 24.9（**省 9%**），代价是中后段反应性变钝。**性价比太低**。若一定要保留一条兜底阶梯，我建议改成 **「事件上限 10 → 6」**（比加长冷却更可控：它只削长尾，不削常态反应性；加长冷却是"所有 agent 都变迟钝"，降上限是"只有连续遭遇的那个 agent 变迟钝"）。

#### 8.4.4 关于「地形 patch 15×15 → 11×11」——我的判断是**不要直接降**，先做另一件事

主理人问 11×11 是否还够 LLM 判断局部地形。我的答复分三层：

**① 15×15 → 11×11 会破坏一条不变式**：`terrainPatch` 半径必须 **≥ `vision.radius`**。
- 15×15 = 半径 7；11×11 = 半径 5；而 **`vision.radius = 9`**（实体可见半径，19×19）。
- 现在的实体清单已经**超出** 15×15 的地形范围（半径 9 > 7）——这是既存的、被容忍的不一致。
- 若降到 11×11（半径 5），LLM 会看到**距离 6~9 格的对手，却没有任何地形上下文**——它无法判断"那个对手和我之间是不是隔着一堵墙"。**这会让事件⑥（对手进入视野）的信息变得无法使用**，而⑥ 恰恰是我们刚花大力气修好的博弈输入。
- **结论：11×11 不可接受。** 若要降，下限是 **21×21（半径 10 ≥ 9）**，那反而比 15×15 更贵。

**② 更该先做的是「砍 ASCII，保留语义导航事实」**。观察里真正驱动决策的是**语义化导航事实**（到各目标的距离 + 下一段航向 + 是否可达），ASCII patch 只是给 LLM 一个"看一眼现场"的冗余通道。设计案 §4.7 已经写了这个结构。降本时**先砍 ASCII**（保留语义事实 + 实体清单），损失远小于缩小 patch。

**③ 顺带更正一处算术**：主理人转的"patch 15×15 → 11×11，token −51%"是**patch 自身**的缩减比（225 → 121 格，−46%）。但 patch 只占单次输入的一部分——单次输入上限 1500 token 里，ASCII patch 约 **250 token**，其余是语义导航事实 + 实体清单 + 历史 + system prompt。**15→11 实际只省约 115 token ≈ 单次输入的 13%、整局的 13%**，不是 51%。

**建议的降本顺序（替换原阶梯②）**：
1. 砍事件⑦（已砍，零成本）
2. **砍 ASCII patch，保留语义导航事实 + 实体清单**（省 ~13%/次，且**不破坏任何不变式**）
3. 事件上限 10 → 6（只削长尾，⚠ 需用户确认——降本本质是"用反应性换钱"，该花多少是用户的决定）
4. 冷却 ≥3 → ≥5（最后手段，实测只省 9%）

**Token 预算**：单次输入 ≤ 1500 token（超预算由 `PlannerCompressor.trimToBudget()` 先把视野窗口 15×15 → 13×13 → 11×11，再裁 `reason` 历史）；单次输出 ≤ 200。整局 token 期望 ≈ 232 次 × 0.9 K ≈ **0.21 M**（最坏 268 次 ≈ 0.24 M）。

### 8.5 超时降级链（对局绝不中断）

| 级别 | 触发 | 行为 |
|---|---|---|
| L0 | `turn.decisionWindowMs = 1500` 到点仍未返回 | 本回合沿用该 agent **上一份 plan**（`source:"cache"`）继续按距离场走一步 |
| L0+ | 迟到结果之后到达 | **写入下一回合的 plan 缓存**（不做回溯修改，保证确定性） |
| L1 | 无缓存 plan / 目标失效 | 转 `HeuristicPolicy`（`core/nav/policy.js`）：**`stamina ≤ d(→exit) * 1.3`** 则回出口（与 #20 罗盘同公式同值，见 §0.3 注），否则取最近的性价比最高宝石；平手按 `actorId` 升序打破 |
| L2 | 单次请求超时 8 s / JSON 不可解析 | 允许 1 次 **repair** 调用（额外 ≤ 150 output token）；再失败转 L1 |
| L3 | 代理不可达 / 连续 3 次 5xx / `429` 持续 | 全局 `aiMode="heuristic"`，HUD 常驻提示"AI 代理离线，已切换本地策略"，**对局继续** |

UI 侧：**硬截止由 `core/scheduler.js` 的看门狗触发，不等任何 Promise**。

### 8.6 Prompt 模板归属

模板文件放 `proxy/prompts/*.md`，由代理拼装 —— 好处：① 玩家自制脚本/自定义提示词作为**数据字段**传入，不被当作指令；② 前端产物里搜不到 system prompt 的硬编码，改提示词只需重启代理，不用重载页面。玩家自定义提示词：**长度截断 2000 字符**，作为 `systemSuffix` 注入。

## 9. 玩家脚本沙箱

### 9.1 隔离手段（诚实版）

| 面 | 手段 | 强度 |
|---|---|---|
| DOM | Web Worker 天然无 DOM | 强 |
| 网络 | ① 页面 CSP `connect-src 'self' http://127.0.0.1:8787`（对 Worker 生效）② worker 前置代码删除 `fetch / XMLHttpRequest / WebSocket / importScripts / indexedDB / caches` ③ 以参数遮蔽 `new Function('self','globalThis','window','fetch',…)` | 强 |
| 文件系统 | Worker 无 fs | 强 |
| 主线程阻塞 | Worker 独立线程 | 强 |
| **CPU 占用** | 墙钟超时 120 ms → `worker.terminate()` | 中（Worker 无法做指令计数，除非做代码插桩，本阶段不做） |
| **主动作弊（改 state）** | ⚠️ **做不到真正防御** | **弱** |

**必须向用户讲清楚的边界**：这是纯本地单机产品，玩家拥有自己的浏览器。沙箱的目标是「**防误触 + 可观测 + 可复盘**」，不是密码学隔离。**真要防作弊，唯一手段是把决策放到权威服务器**——但这与"零后端"的产品纪律冲突，因此**明确不做**。兜底手段是：所有脚本决策写进 JSONL，回放可审计；若日后要做联机/排行，再引入服务端权威（那是另一个产品形态，需重新评估）。

### 9.2 资源限制

| 项 | 规则 |
|---|---|
| 单次决策墙钟 | ≤ 120 ms，超时 `terminate()` + 重建 Worker |
| 超时时的动作 | 取该脚本**上一回合的决策方向**复用；无则 `"STAY"`（确定性，不是随机） |
| Worker 重建后状态 | **脚本必须无状态依赖**：跨回合状态放在主线程托管的 `stateBag`（`JSON.stringify` 往返，**上限 16 KB**，超限截断并 warn） |
| 无限循环预判 | 载入时用正则拒绝 `while(true) / for(;;)` 并给友好提示（不是可靠手段，只是防手滑） |
| 异常隔离 | 脚本内 `try/catch` 包住用户函数；抛错 → 该回合 `"STAY"` + 记录 `error`，**不影响其他 actor 与对局** |
| 连续失败 | 同一脚本连续 10 回合异常 → 自动切回手动输入并提示玩家 |

### 9.3 暴露给脚本的只读 API（签名）

```ts
// 每次决策调用一次：decide(obs, api)
interface Obs {
  turn: number;
  self: { id; x; y; stamina; score; gems: string[]; exitColor: string; atExit: boolean };
  visible: {
    tiles: Uint8Array;   // 视野窗口可读部分之外的格子为 UNKNOWN(0)
    origin: { x; y }; w; h;
    gems:   { x; y; color }[];
    chest:  { x; y } | null;
    actors: { id; x; y; color; isPlayer }[];   // 仅视野/记忆内
  };
  remember: { chest: {x;y}|null; exit: {x;y}|null; gemsSeen: number };  // 依视野模式
  rules: Readonly<RulesSnapshot>;   // 冻结对象，改它无效
  state: unknown;                   // 上一回合自己存的状态
}
interface Api {
  move(dir: 'N'|'S'|'E'|'W'|'STAY'): void;   // 调用后必须立即 return
  shortestStep(tx, ty): Dir | 'BLOCKED' | null;   // 只允许查询「可见或记忆」的目标
  distance(tx, ty): number | -1;                   // 同上
  setState(v: unknown): void;                      // ≤16KB
  log(...args): void;                              // 写入本地回放日志
}
```

**反探测硬门槛（重要）**：

1. `shortestStep / distance` **只接受在 `visible` 或 `remember` 集合中的目标**，否则直接返回 `-1`。否则脚本可用反复距离查询做"三角定位"，把整张地图扫出来，让任何视野模型失效。
2. **每次决策最多调用 8 次寻路**（`script.navCallBudget = 8`），超出后一律返回 `-1`。
3. 单个决策周期内不可遍历超过视野窗口的 tile。

**单一可见性来源承诺**：`rules/vision.js: buildObservation(state, actorId)` 同时喂给 ① 玩家渲染裁剪 ② Worker 沙箱载荷 ③ LLM 观察快照。三者拿到的一定是同一份规则——这是"AI、脚本、人类三者公平"的**唯一强制手段**，任何地方都不许直接读原始 state。

## 10. 视野模型（可配置，三种都支持）

用户已否掉战争迷雾（未探索区域全黑）。下表三个候选**均已做成配置开关**，创意总监随时可切，不改渲染层：

| 模式 | 效果 | 实现要点 | 渲染影响 |
|---|---|---|---|
| **① `full-terrain-dynamic-entities`（默认建议）** | 地形全公开；只有宝石/宝箱/其他角色受视野半径限制 | 静态层照常全画；动态实体按 `visible` 集合过滤 | 无额外成本 |
| ② `radius+memory` | 视野半径内全可见；半径外的地形与实体显示"上次看到的样子" | 每 actor 维护 `knownTiles: Uint8Array`（16 KB/人），更新时脏标记 | 需额外维护记忆层，渲染侧要按记忆贴图，**预估帧率影响 < 5%**（P1.5 实测后再定） |
| ③ `full-open-clipped` | 全公开，只做渲染裁剪 | 全静态 + 全动态 | 最省，但博弈性最弱（无信息优势） |

**内存成本**：记忆数组很小——①模式每人一份"已见实体表"（< 1 KB），②模式每人一份 `Uint8Array(16384)` = 16 KB，四角色合计 64 KB，可忽略。真正的成本在 UI 侧要不要把"记忆中的旧状态"画出来（②模式才需要），这是 P2 的取舍，不影响架构。

**对 AI 与沙箱的兼容性**：三种模式都不给任何一方全量动态信息，**沙箱 API（§9.3）与 LLM 观察（§8.3）都走同一份 `buildObservation`**，切换视野模型不需要改 AI、沙箱或渲染主体的代码。

**实体级可见性（D6 附带裁定）：唯一的不对称信息是"对手在哪"**

| 实体 | 是否受视野限制 | 理由 |
|---|---|---|
| 地形 | ❌ 全公开 | 用户已否掉迷雾 |
| **宝石 / 宝箱位置** | ❌ **全局公开**（开局广播，重生时再广播） | 128×128 里盲找 5~10 颗是迷路，不是博弈 |
| **其他角色位置** | ✅ 受 `vision.radius = 12` 限制 | 保留唯一的信息差，也是伏击/抢点的空间 |

实现要点：宝石/宝箱坐标不进 `visible` 过滤，直接进 `remember`（永久记忆）；只有 `actors` 数组走 `visible` 过滤。`buildObservation` 里这是三行开关，三者（渲染/沙箱/LLM）仍然同份数据。
